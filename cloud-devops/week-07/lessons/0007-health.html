Week 07 / Lesson 07

Make health claims precise

Implement two endpoints whose status codes match the claims they make.

Our /health answers “can this API respond?” Our /ready answers “can its required dependency probes succeed now?” These meanings are our explicit application contract, not magic attached to the path names. A green /health must not hide a broken queue; a broken queue must not make a responsive API disappear from diagnostics.

Work a truth table first

Read operations.py and the readiness cases in tests/test_contract.py. Both postgres and redis must be exactly True. A missing key is failure. Vector is a placeholder; it does not block ingestion readiness. Store the four two-dependency combinations and predictions in your weekly log before writing code.

The completed practice chooses 503 for {"db": True, "queue": False}. It sees one false value, so all is false. But all([]) is true: an empty list has no false elements. Your project's required-key policy must avoid that trap; checking only whichever keys happen to be present is insufficient. Build the required-key result first, then compute its status.

From Week 7, edit only readiness first, then run:

.venv/bin/python -m pytest -q projects/local-stack/tests/test_contract.py -k readiness

Six cases should pass after implementation. A return value like ({"ready": False}, 503) is not the documented tuple order. Fix the contract rather than the test.

Turn policy into HTTP

Read fixture/probes.py. Its supplied adapters perform SELECT 1 using app credentials and Redis PING with bounded socket waits. Exceptions become false, not leaked connection strings. Read the demo routes in practice/mechanisms.py: @app.get registers the following function; JSONResponse(content, status_code=503) sends a real HTTP status. Returning a dict with a “status” field alone sends the default 200.

Implement install_health in operations.py. Accepting a callable instead of hardwiring the database lets a test substitute one. A plain def route lets FastAPI run these synchronous I/O calls in its thread pool; calling them directly inside an async def route would block its event-loop thread. Recheck on every /ready request. Catch a probe exception at this boundary and use both required checks false. /health must not call the probe at all.

.venv/bin/python -m pytest -q projects/local-stack/tests/test_contract.py -k "readiness or routes or probe"

Expect eight tests passing. Record one failure you fixed and the cause. Then add the API Compose health check calling http://127.0.0.1:8000/ready from inside that container with Python's urllib.request (already installed). The probe timeout should exceed the combined bounded dependency waits; use 10 seconds. You do not need curl in the slim image.

Hint · open after trying

Separate normalizing required booleans, deciding status, and registering routes.

Explained answer · compare your reasoning

Use checks.get(name) is True for each required name. The public body contains only normalized booleans. Register /ready to call the injected checker and return JSONResponse with the chosen status. Register /health separately with {"alive": True}; do not reuse dependency logic there.

Independent variation: write a test that changes one dependency from false to true between requests. Explain why SELECT 1 does not prove the ingestion table exists, a transaction can commit, or a worker is consuming jobs. The live job check supplies evidence those probes cannot.

Primary reading: fastapi.tiangolo.com · official documentation. Use it to check this mechanism, then return to your own example.
