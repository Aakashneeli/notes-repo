Follow one request through middleware

Correlate successful and failed HTTP responses without leaking request content.

A request ID is a label shared by the response and its log event. It helps find related observations; it is not authentication or a guarantee of uniqueness when a client supplies it. A job ID names durable work and is a different concept. The fixture stores the request ID with the job, but its RQ logs do not automatically propagate HTTP context.

Trace the smallest wrapper

Read the marker middleware in practice/mechanisms.py. async def defines a function that can yield while awaiting work. await call_next(request) runs the downstream request handling and resumes with a response. The wrapper adds X-Lesson then returns it. Trace: before wrapper → route → response object → header added → client. Its 503 demo proves headers can be added to error-status responses too.

Our request wrapper additionally chooses a safe ID before calling downstream and stores it on request.state.request_id, per-request storage. Never use one global variable; overlapping requests would overwrite it. Use time.perf_counter() before/after the call; subtract and multiply by 1000 for elapsed milliseconds. A monotonic clock measures duration without wall-clock adjustments.

Implement and check the small policy

From Week 7, edit request_id in observability.py. A client candidate is acceptable only if it contains 1–64 ASCII letters, digits, underscores or hyphens. A full regular-expression match checks the entire string, unlike searching for a valid substring. re.fullmatch(r"[A-Za-z0-9_-]{1,64}", candidate) requires checking for None first. Otherwise uuid4().hex generates a 32-character hexadecimal replacement. Python's isalnum accepts more than ASCII, so it alone does not satisfy this contract.

Read the install_logging contract and log tests before implementing the wrapper. Normal handled errors such as 404 return a response from call_next. An unexpected exception may instead escape that call; catch Exception at this HTTP boundary, create the sanitized JSON 500 response, and still add the correlated header and emit exactly one event. Do not include the exception message. Keep the response construction and final logging path common so you do not double-log an error.

Explained answer · compare your reasoning

The wrapper sets request.state.request_id, tries awaiting call_next, and on an unexpected exception chooses JSONResponse({"detail": "internal_error"}, status_code=500). After either path, add the response header, emit the allowlisted event using response.status_code and elapsed time, and return that response. Do not catch process-exit/cancellation signals by catching BaseException.

This is an intentionally bounded teaching policy: sanitizing unexpected failures is useful, but a production system also needs a protected diagnostic channel for actionable stack traces. Do not silently put confidential exception strings into the public log to compensate.
