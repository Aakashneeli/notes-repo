Week 07 / Lesson 06

Keep data through container replacement

Separate service startup, dependency readiness and persistent state.

“Container started” means its process launched. Postgres may still be initializing. depends_on with a health condition waits for a configured health check before starting a dependent service. It is a startup gate, not continuing recovery orchestration. A dependency can fail after your API starts.

Add one readiness gate at a time

From Week 7, continue editing compose.yaml using service-contract.md. For Postgres use its installed pg_isready; for Redis use redis-cli ping. This fragment illustrates shell expansion inside a health test:

healthcheck:
  test: ["CMD-SHELL", "pg_isready -U $$POSTGRES_USER -d $$POSTGRES_DB"]
  interval: 5s
  timeout: 3s
  retries: 10
  start_period: 10s

CMD-SHELL runs a shell; $$ prevents Compose from consuming the variable so the container's shell can expand it. CMD array form invokes a program directly and does not expand shell variables. interval schedules probes; timeout bounds one; retries bounds consecutive failure tolerance; start_period allows warm-up. pg_isready asks whether the server accepts connections; it does not prove the application password, table or query works.

Wire api to healthy postgres/redis. Its command must run python -m fixture.bootstrap successfully before replacing the shell with Uvicorn using exec. The worker uses the same built code with a different RQ command, waits for Redis/Postgres and a healthy API (after Lesson 7), and consumes the ingestion queue. Matching the import path and queue name is essential. Qdrant is an independently reachable placeholder, not an API readiness prerequisite.

Predict what survives

A container writable layer goes away when the container is removed. A named volume has a separate lifetime. For postgres:16-alpine mount pgdata at /var/lib/postgresql/data; Redis append-only data goes to /data; Qdrant storage to /qdrant/storage. Declare each named volume at top level and mount it under its service. A bind mount instead exposes a specific host path, useful for editing source but less portable for this fresh-clone exercise.

The tiny fixture stores the submitted text in Postgres, so it does not need a shared upload directory. A completed Week 6 local-file backend would require a shared named volume mounted at the same configured location in both API and worker. Capture that difference in bridge-notes.md instead of claiming the fixture reproduces Week 6 storage.

After finishing the app hooks in Lessons 7–9, start at Week 7 and run:

cd projects/local-stack
docker compose --env-file .env.example up --build --wait --wait-timeout 120
docker compose --env-file .env.example ps
docker compose --env-file .env.example logs --tail=30 postgres redis
cd ../..

Expected: readiness gates pass, API healthy, worker running; vector running alone is weaker evidence than its later HTTP probe. On insufficient memory inspect exit codes and local resource use; do not add paid capacity. Put observations in the weekly log, then use Lesson 10 for real job and persistence checks. No running services are required to write/test the health policy now.

Hint · open after trying

If Postgres data already exists, do environment variables recreate its users?

Explained answer · compare your reasoning

No. Initialization variables apply to an empty data directory. A changed password in Compose does not rotate the password in an existing volume. Diagnose the mismatch and use the existing lab credentials or deliberate SQL rotation; do not erase data as a default fix.

Variation: predict what survives docker compose down followed by up, then compare with container recreation. This course never asks you to delete volumes. Explain why volume persistence is not a tested backup or a guarantee of atomic Postgres-plus-Redis writes.

Primary reading: docs.docker.com · official documentation. Use it to check this mechanism, then return to your own example.
