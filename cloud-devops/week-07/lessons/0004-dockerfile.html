Week 07 / Lesson 04

Package the ingestion application

Write the build recipe and explain every path from host context to runtime import.

For this project, the build context is the Week 7 root; the Dockerfile lives deeper. These are independent choices. The host's projects/local-stack/app.py will become /app/app.py. Uvicorn imports that file at runtime. Copying from outside the context does not work.

From a tiny image to an API

Start at Week 7. Read .dockerignore: the allowlist sends only the lockfile and runtime code. It prevents a broad COPY from including notes, environments or credentials. Open and edit projects/local-stack/Dockerfile; it is intentionally comments only. Read app.py: the supplied factory registers the bridge router, then calls your unfinished health and logging hooks.

Your recipe needs a Python 3.12 slim base, WORKDIR /app, unbuffered output, a copied lockfile and dependency installation, copied runtime code, and an exec-form Uvicorn command. A worked dependency step for a different small app would be:

COPY deps.txt /app/deps.txt
RUN python -m pip install --no-cache-dir -r /app/deps.txt
COPY sample.py /app/sample.py
CMD ["python", "sample.py"]

RUN executes during build; CMD describes the runtime default. Copy dependency declarations before source so a source edit can reuse the expensive installation layer. JSON-array command form supplies executable and arguments directly. Our factory target is app:create_app, with --factory --host 0.0.0.0 --port 8000 --no-access-log. Disabling default access logs avoids leaking query strings alongside your safe Week 7 event. 0.0.0.0 listens on container interfaces; it is not the URL you type in a browser. EXPOSE documents a port but does not publish it.

Install from requirements.lock. This intro lock includes test tools in the image to keep the dependency story simple; record that image-size tradeoff. Runtime credentials must come from Compose, never a Dockerfile instruction. Installing dependencies is a build action; connecting to PostgreSQL during build is a design error because build should not depend on a running database.

docker build -f projects/local-stack/Dockerfile -t week7-api:local .
docker image inspect week7-api:local --format '{{json .Config.Cmd}}'
docker run --rm --entrypoint python week7-api:local -c "import app; print('import ok')"

Run from Week 7 root. Expect the correct Uvicorn command and import ok; these do not call the factory. A full startup still raises NotImplementedError until Lessons 7–9. Record the build output and what it proves. If COPY fails, compare context-relative paths, not just the Dockerfile directory. If Uvicorn cannot import app, check WORKDIR and destination paths. Explained answer · compare your reasoning

The project directory is not the context in our build command. The source copy must name projects/local-stack/. Inside the image app.py must sit directly in /app so importing app succeeds from WORKDIR /app.

Variation: change the host publish port later without rebuilding. Explain why that change belongs to run configuration, unlike a source edit. Optional hardening decision: run as a non-root image user after verifying file permissions; do not confuse that with database roles.

Primary reading: docs.docker.com · official documentation. Use it to check this mechanism, then return to your own example.
