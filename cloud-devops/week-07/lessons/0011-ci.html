Week 07 / Lesson 11

Make checks repeat on a clean runner

Write a push/PR workflow and explain each process and working directory.

Continuous integration runs repeatable checks when code changes. A runner is a fresh machine executing a job; steps within that job run in order. A nonzero command exit fails the step. Ruff catches selected code errors without running the application; pytest executes tests. Neither proves your live Compose stack works unless that behavior is explicitly exercised.

Run the same checks first

From Week 7 root:

.venv/bin/python -m ruff check .
.venv/bin/python -m pytest -q

Default pytest includes learner exercises and project contracts, so it must remain red while they are unfinished. The earlier targeted author suite passing is not a substitute. Read ci/workflow.yml and edit it. It is deliberately staged under the project and inactive. GitHub discovers workflow files only under the repository-root .github/workflows directory. No remote action occurs while it stays here.

Understand the workflow vocabulary

on: [push, pull_request] names triggers. jobs maps job names to their configuration. runs-on: ubuntu-latest chooses a runner. A uses step runs a versioned action such as checkout or setup-python. A run step runs shell commands. permissions: contents: read limits the job token to checkout needs.

A small unrelated step illustrates working directories:

- name: Read interpreter version
  working-directory: tools/example
  run: python --version

The directory must already exist after checkout. For this notes repository, the correct default run directory is cloud-devops/week-07. Specify it under the job's defaults.run.working-directory. Checkout itself is a uses step and is not relocated by run defaults. Set Python 3.12, install -r requirements.lock, then use python -m ruff check . and python -m pytest -q. A fresh runner has no .venv or imported modules from your terminal; installation and pyproject paths are essential.

The inspected official example uses actions/checkout@v6 and actions/setup-python@v5; the action version is separate from python-version: "3.12". Use those documented versions for this exercise and recheck when updating; record selected action versions in decisions.md. Immutable commit SHAs provide stronger pinning than moving action tags, but a reviewed documented major version is adequate for this introductory local draft. Do not add credentials or deployment steps.

Make the failure explainable

In a disposable learner test, write assert 2 == 3, run that test and observe a nonzero exit, then restore it and rerun. Or use an actual unfinished contract failure. Record the exact command, failure explanation and passing rerun in ci-evidence.md. This is local evidence, not a hosted GitHub Actions run.

Run .venv/bin/python maintenance/check_project.py from Week 7 after completing your configuration. It checks structural omissions, including inactive-workflow content, without sending anything to GitHub. The author can check the checker, but cannot manufacture your assessed workflow or a passing learner run.

Explained answer · compare your reasoning

A job has runs-on, defaults, and a steps list. Include checkout and setup-python, then three run steps for pip, Ruff, and pytest. Both lint and test need the same Week 7 working directory. Do not use continue-on-error or || true: those would turn a broken gate into apparent success.

Later learner action only: after reviewing the finished file and existing workflows, copy it to the notes repo's .github/workflows/week-07.yml without overwriting an existing file. A chosen GitHub repository, Actions permissions and any applicable minutes/billing limits are prerequisites to a hosted run. Publishing, pushing or changing settings is not part of preparing this material. Mark hosted CI “not run” until a real run URL and commit exist.

Primary reading: docs.github.com · official documentation. Use it to check this mechanism, then return to your own example.
