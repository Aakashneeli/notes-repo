Week 07 / Lesson 10

Diagnose the running stack

Find the failing layer with a probe, then prove the repair with a real job.

Start with a falsifiable guess: “DNS is wrong” predicts name resolution failure; “worker stopped” predicts an accepted pending job without completion. Avoid changing multiple layers at once. From Week 7, open debugging-note.md and use templates/mistake.md for symptom, prediction, smallest probe, cause, fix and regression evidence. Do not invent a failure you never saw.

Observe before changing

cd projects/local-stack
docker compose --env-file .env.example ps -a
docker compose --env-file .env.example logs --tail=50 api worker
docker compose --env-file .env.example exec api sh
pwd
python -c "import socket; print(socket.gethostbyname('postgres'))"
exit
cd ../..

The shell steps run inside the API; expect /app and a network IP. Do not edit container source as a permanent fix—it vanishes on replacement. exit returns to projects/local-stack on the host before cd ../... If api is stopped, exec cannot enter it; use logs first or docker compose --env-file .env.example run --rm --no-deps api sh for an isolated diagnostic shell. No shell probe should print your environment secrets.

Port already allocated: run ss -ltn on the host, find 8077, and select a free host port with API_PORT=8078 docker compose --env-file .env.example up -d; do not kill an unrelated service. Inside binding remains 8000. Missing import: inspect Dockerfile context and WORKDIR. Name resolves but connection refused: inspect the target process, port and readiness. Permission denied on a volume: inspect intended ownership before changing anything broadly.

Check actual work, not just a green light

Read the supplied smoke.py and data/hello.txt. The sample is public and contains 17 characters including its newline. From Week 7 root after starting your stack:

.venv/bin/python projects/local-stack/smoke.py
cd projects/local-stack
docker compose --env-file .env.example exec api python -c "from fixture.probes import vector_check; assert vector_check(); print('vector reachable')"
docker compose --env-file .env.example logs --no-log-prefix --tail=30 api
cd ../..

Expect a job ID and characters 17, then vector reachable. If you changed API_PORT, set LAB_URL=http://127.0.0.1:8078 before the smoke command. If you use a private .env API_KEY, supply that key through the host environment; the Python script does not read Compose's env file automatically. Record the ID, outputs and log event for smoke-7 in the weekly log. This script writes one sample job; it requires real local services. The vector probe proves only its HTTP readiness response, not embeddings or retrieval.

Two controlled failures

Start in projects/local-stack. Stop only this lab's Redis with docker compose --env-file .env.example stop redis. From another host terminal, curl -i http://127.0.0.1:8077/health should return 200 and /ready 503. Restart Redis with docker compose --env-file .env.example start redis, wait for readiness, then confirm 200. A Compose restart policy does not cure a dependency outage.

Next stop only worker, submit the sample with the command below, and save the returned ID. The API can remain ready because dependency connectivity does not prove consumption. Start worker and poll that job; expect eventual completed. Recovery from an actual mid-job crash remains a fixture limitation.

curl -i -H 'X-API-Key: week7-practice-key' -H 'Content-Type: text/plain' --data-binary @data/hello.txt http://127.0.0.1:8077/documents
# Replace JOB_ID with your returned identifier:
curl -i -H 'X-API-Key: week7-practice-key' http://127.0.0.1:8077/jobs/JOB_ID

Finally, with no jobs running, run docker compose --env-file .env.example down, then the documented up command. GET the saved completed job again: named-volume persistence should retain it. Never add volume-deletion flags. Record actual results, a debugging note and a regression test in tests/test_learner.py; then move to CI.
