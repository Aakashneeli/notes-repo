The source's four explain-backs

  1. What is inside your image, and what exists only at container runtime? Name a real file, variable and volume.
  2. How does the API find Postgres/Redis inside Compose? Draw caller → DNS → container port.
  3. What does your health check prove and what does it not prove? Include the stopped-worker counterexample.
  4. Where do logs go locally, and how would that change in AWS? Separate emitting JSON from configuring its destination.

Give each explanation from memory, then demonstrate one observation supporting it. If an explanation is weak, return to the corresponding lesson and retry a different example. “I read the page” is not evidence.

Reduce help, then delay

First attempt the normal stack using only your runbook. Next use a different host port, fail one dependency, and predict health/readiness and job behavior before observing it. After roughly two days, redraw the topology and reconstruct the Dockerfile's instruction order without opening it. About a week later, explain a new failure such as wrong queue name or a stale image. Flexible timing is fine; record the actual date and help used.
