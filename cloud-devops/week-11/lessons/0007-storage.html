Week 11 · 07

Choose storage and a runtime deliberately

Explain S3, RDS, EC2, ECR/ECS and Lambda by the responsibility each owns.

Storage and compute solve different problems. EC2 runs a virtual machine you maintain. ECR holds container images. ECS schedules containers: a task definition describes them, a task is one running instance, and a service keeps the desired count running. Fargate supplies managed compute capacity; ECS can also use EC2. ECR does not run your app, and adding ECS does not make the surrounding network/log/storage bill disappear.

Lambda runs event-driven functions with a configured execution timeout, currently up to 900 seconds. A small file-validation event can fit; a job that may run for 25 minutes cannot rely on one invocation. Retries, cold starts, external state and concurrency still need design. Long model work may belong on a worker, with a queue and job state. This is awareness, not a request to deploy three platforms.

Object versus row

S3 stores objects addressed by bucket and key: bytes such as uploads/document.txt. A relational DB stores queryable records and relationships: document ID, owner, object key and processing state. Updating a row and uploading an object are not one automatic transaction; interrupted work can leave an orphan object or a row pointing to missing bytes. A reconciliation/retry strategy must identify these states.

RDS manages database infrastructure tasks while you still own schema, queries, access and restore verification. An external low-cost PostgreSQL service can be acceptable for this budget if TLS, access controls, backup/restore, region latency, connection limits and data policy fit. Compare actual pricing and sleep/usage limits; do not select solely from a “free” label. A local container filesystem is not a durable database plan.

Decide whether the conditional S3 lab applies

At the week root edit storage.md. The supplied fixture has no upload/storage requirement; it may honestly mark S3 integration not applicable. If you use an earlier ingestion service, S3 applies: keep its metadata in the DB and add/test object persistence in the actual app. Do not confuse a CLI upload with app integration.

data/sample.txt contains harmless sample bytes. For an applicable live lab, the learner first creates a private bucket in the chosen region, keeps Block Public Access enabled, selects encryption/lifecycle settings, and scopes the workload role to the required prefix. GetObject/PutObject use object ARNs; listing uses the bucket ARN. Preserve the bucket name only in private operational configuration if desired.

# LEARNER LIVE ACTION, from week root with authenticated AWS CLI.
# Set WEEK11_BUCKET to your already-created private bucket first.
aws s3 cp projects/deployment/data/sample.txt "s3://${WEEK11_BUCKET:?}/uploads/sample.txt"
aws s3 cp "s3://${WEEK11_BUCKET:?}/uploads/sample.txt" /tmp/week11-returned.txt
cmp projects/deployment/data/sample.txt /tmp/week11-returned.txt

Use a fresh local destination if that /tmp file already contains your work. No output from cmp means equal bytes; nonzero means mismatch/error. Record object key, byte comparison, private-access check and actual app round-trip separately in storage.md. Test an unauthenticated object request receives denial; do not disable protection to “fix” it. If no live lab is possible, leave this evidence pending.

Prediction, hint and answer

Your API host disappears. Which survives: memory, unbacked container writes, S3 object, RDS row? The first two cannot be relied on; S3/RDS exist independently, subject to their deletion/retention settings. “Independent” does not prove your application can reconnect or your backups restore.

Variation: choose a 20-minute summarization job and a 2-second metadata event. Defend a runtime for each using duration, state and cost. Record your choice, not just a service name. Next: automate checks before release.
