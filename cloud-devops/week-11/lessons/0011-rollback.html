Promote only a verified release

Implement a release gate and recover from a failed candidate without confusing code and data rollback.

A deploy command can succeed while the application is wrong. Promotion means choosing a candidate for normal traffic. Rollback selects the previous known-good image and compatible configuration. Tags can move, so keep the image digest or an explicitly recorded local image ID as evidence.

A gate with two distinct checks

A health response of 200 from release old is not proof of release new. A ready field equal to the number 1 is not the JSON boolean true required by this contract. Python considers 1 == True equal; ready is True tests the exact boolean object. The gate needs status 200, exact True readiness, matching nonempty release strings.

At the week root edit release.py. It is a pure decision function; no hidden script deploys for you. Read the supplied test_release.py; its parameterized table calls the same function on different cases. Then run:

cd /home/an10/code/notes-repo/cloud-devops/week-11
.venv/bin/python -m pytest projects/deployment/tests -q
First hint

Write four required conditions in words, then combine them. A single false condition must block promotion. Do not treat the status as a truthy integer.

Second hint

Separate “is the expected release nonempty?” from “do the strings match?” Otherwise two empty strings would pass. Add an independent test before implementing the whole expression.

The assessed implementation is yours. Add a test for a new failure or input boundary in the same tests directory; explain what mistake it catches. A gate tested in isolation does not prove your runbook actually uses it.

Break a local candidate safely

Start the good lesson 4 container on port 8000. In another terminal at the week root, run a candidate on 8001 with a public dummy environment and a known injected failure:

docker run --rm --name week11-candidate -p 127.0.0.1:8001:8000 \
  --env-file projects/deployment/.env.example \
  -e RELEASE=week11-bad -e FAIL_MODE=dependency week11-api:v1

In a third terminal at the week root:

curl -i http://127.0.0.1:8001/health
curl -i http://127.0.0.1:8001/ready
curl -i -H 'X-API-Key: local-rehearsal-only' http://127.0.0.1:8001/message
curl -i http://127.0.0.1:8000/ready

Predict then observe: 200, 503, 500, and the old release still ready. The bad image here is the same code with faulty config; code replacement alone cannot repair that. Stop only the candidate with Ctrl-C. Record the observations in rollback.md. Recreate a healthy candidate with RELEASE=week11-v2 and empty FAIL_MODE, verify all three route types plus unauthorized access, then remove it when finished.

A concrete single-host switch

Command pattern — learner live action after candidate checks

Start on the host in /home/ubuntu/week11-runtime. Before switching, create a separate mode-600 .env.candidate in your editor, validate it on port 8001, and set WEEK11_CANDIDATE_IMAGE to the exact tested digest/local image ID. Confirm that the archive name below is unused with sudo docker ps -a. The pattern accepts a brief outage.

sudo docker stop week11-api
sudo docker rename week11-api week11-previous-v1
sudo docker run -d --name week11-api --restart unless-stopped \
  -p 127.0.0.1:8000:8000 --env-file .env.candidate \
  --log-driver local --log-opt max-size=10m --log-opt max-file=3 \
  "${WEEK11_CANDIDATE_IMAGE:?}"
curl -i http://127.0.0.1:8000/health
curl -i http://127.0.0.1:8000/ready

Use lesson 9's private authenticated request too, then repeat through the tunnel. If the new container fails, remove only that new container and restore the archive:

sudo docker stop week11-api
sudo docker rm week11-api
sudo docker rename week11-previous-v1 week11-api
sudo docker start week11-api
curl -i http://127.0.0.1:8000/health
curl -i http://127.0.0.1:8000/ready

If creation failed before week11-api existed, skip stop/rm and restore the archive. Record actual results in rollback.md. This pattern uses local logs; if cloud logging was selected, preserve the verified lesson 10 options and check delivery too. Never overwrite the old configuration with the faulty candidate's file. See Docker run and Docker rename.

For a real release, keep the old image and config version. Verify a candidate on port 8001 first, using the real key privately. Our simple direct port mapping cannot atomically switch traffic; accept a short maintenance window. Stop the old container, rename it to a unique archived name, and create the new week11-api on port 8000 using the candidate's verified image and config. Immediately run health, readiness, authorized and unauthorized checks through the actual tunnel. Write exact commands for your chosen digest in rollback.md before attempting it.

If the new release fails: stop/remove only that new container, rename the archived previous container back to week11-api, start it, and repeat the endpoint checks. Its original creation-time environment is retained. Never delete the old image/config before recovery is proven. Existing database migrations may make old code incompatible; a code rollback cannot un-delete rows. For a real data app, plan backward-compatible schema changes or an independently verified restore/forward-fix strategy.

Independent variation: candidate readiness is good but the returned release is old. Explain why the gate must reject it. Update CI's release tests from lesson 8 and rerun the local pipeline. Next: prove that stopping work also stops avoidable cost.
