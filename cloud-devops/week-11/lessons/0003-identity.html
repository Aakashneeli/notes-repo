Separate identity from network access

Explain one allowed action and one denied connection using distinct boundaries.

Authentication answers “who?” Authorization answers “may this identity do this action to this resource?” Networking answers “can packets get there?” SSH access does not grant S3 permission, and an IAM Allow does not open a port.

A small policy trace

An IAM user is a persistent identity; a role is assumed for temporary credentials. Prefer federated human login with MFA and a workload role for EC2. Protect root and avoid using it for routine deployment. A role has two different policies: its trust policy identifies who may assume it; its permissions policy says what the resulting session may do.

Worked example: EC2 assumes a role trusted by ec2.amazonaws.com. Its permission allows s3:GetObject on arn:aws:s3:::example-week11/uploads/*. Reading uploads/a.txt can match; deleting it does not match that action; reading private/b.txt does not match that resource. An explicit deny or another applicable boundary can still block an allow. A bucket ARN and an object ARN are different resources; ListBucket uses the bucket ARN. Least privilege is a testable scope, not merely a reassuring role name.

Trace a connection separately

A security group is an allow-list around a network interface. An inbound rule for TCP 22 from your current public IP /32 permits SSH from that single IPv4 address. 0.0.0.0/0 means any IPv4 source. Outbound rules govern initiated outbound traffic; security groups are stateful, so responses to allowed traffic are tracked. DNS, image downloads, registry and logging need reachable destinations. Rules alone cannot fix a missing route.

In access-plan.md, fill the human identity, EC2 role and source CIDR sections. Use documentation addresses in exercises; replace them with your actual address only in your private operational settings. Do not put access keys in this file.

Practice a deliberately smaller model

At the week root, implement rule_allows in practice/exercises.py. It compares labels exactly, plus the special wildcard source. It intentionally cannot interpret arbitrary CIDRs, protocols, routing, egress or IAM policies. That limitation makes the trace visible, but it is not an AWS validator.

cd /home/an10/code/notes-repo/cloud-devops/week-11
.venv/bin/python -m pytest practice/test_exercises.py -k rules -q
Hint

For each dictionary in rules, both the port and a permitted source must match. Matching only the source accidentally opens every port.

Explained answer
return any(
    rule["port"] == port and rule["source"] in (source, "0.0.0.0/0")
    for rule in rules
)

An empty list produces False. The test with port 8000 catches a forgotten port comparison; the changed source catches accidental public access.
