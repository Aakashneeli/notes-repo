Week 11 · 08

Make CI earn the right to release

Write a test/build workflow and explain the separate deployment identity boundary.

Continuous integration runs checks on a proposed change. Delivery produces a releasable artifact; deployment changes the running service. A green syntax check cannot prove the candidate is healthy in its destination. This week requires lint/test/build plus a documented deploy step; automatic cloud deployment is not necessary.

Trace a small job

jobs:
  verify:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: cloud-devops/week-11
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: python -m pip install -r requirements.lock

YAML indentation makes a mapping nested; - starts a sequence item. Checkout obtains source; setup-python chooses an interpreter. The run default changes shell commands' directories, not uses actions' input paths. This fragment is a worked example, not a complete project workflow. These major tags illustrate syntax; before activating a workflow review the action's release and pin a reviewed full commit SHA for stronger supply-chain control.

Edit the inactive workflow.yml. Keep push/pull_request triggers and contents: read. Add install, Ruff, fixture tests, release tests and Docker build. Gate publishing/deployment on successful checks; untrusted pull requests must not receive cloud credentials. Do not run cloud deployment under pull_request_target with untrusted checked-out code. Include a manual deployment description in runbook.md naming the exact tested commit and artifact.

ECR push and deployment are distinct

With learner-owned AWS/GitHub setup, an optional trusted release job can exchange GitHub's OIDC token for an AWS role session. The trust policy must match aud=sts.amazonaws.com and a specific repository/branch or protected environment subject. id-token: write permits requesting the token; it does not grant AWS permissions. The assumed role still needs narrowly scoped ECR push permissions. The EC2 host needs only pull and log permissions. Never distribute a root or long-lived deployment key to a PR job.

# LEARNER LIVE ACTION, after identity and repository are configured:
aws ecr get-login-password --region "${AWS_REGION:?}" |
  docker login --username AWS --password-stdin "${WEEK11_REGISTRY:?}"
docker tag week11-api:v1 "${WEEK11_REGISTRY:?}/week11-api:${WEEK11_RELEASE:?}"
docker push "${WEEK11_REGISTRY:?}/week11-api:${WEEK11_RELEASE:?}"

WEEK11_REGISTRY is the account/region registry hostname; WEEK11_RELEASE identifies the tested commit. ECR must have the repository (or an explicitly configured creation template). Record the resulting digest; avoid deploying an ambiguous mutable latest tag. The EC2 lesson also offers image transfer without registry setup.

Hint and debugging feedback

“requirements.lock not found” often means a wrong working directory. “Not authorized to assume role” points to the token/trust relationship; “denied pushing image” after successful role assumption points to permissions/resource scope. They are different boundaries.

Variation: make a fixture assertion fail on a scratch branch; predict whether image publishing can still run. Add one source-reading note about needs/permissions, then continue to the host rehearsal.
