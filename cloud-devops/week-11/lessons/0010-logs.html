Week 11 · 10

Follow an incident through logs and health

Use a request ID and release to investigate a 500 without leaking secrets.

Health asks whether the process responds; readiness asks whether this instance should receive work. Logs explain events. None substitutes for a meaningful authenticated request. Our fixture intentionally lets /health remain 200 while /ready is 503 and a protected route returns 500 under a simulated dependency failure.

Read an event as evidence

Read practice/data/events.jsonl. JSON Lines means each line is its own JSON object, not one enclosing list. The r02 event failed on release b2; r01 succeeded on a1. That suggests a release-related hypothesis, not proof. The dependency could have changed at the same time. Correlate timestamp, request ID, release and status before changing anything.

At the week root run practice/examples.py again and trace json.loads for each line, then the status comparison. Edit failing_requests in practice/exercises.py and run:

cd /home/an10/code/notes-repo/cloud-devops/week-11
.venv/bin/python -m pytest practice/test_exercises.py -k events -q
Hint

Make an empty result list; visit each dictionary; append its ID only if status is at least 500. Preserve input order.

Explained beginner answer
return [event["request_id"] for event in events if event["status"] >= 500]

The expression selects IDs, not entire records. A 499 is not a server-error status; the boundary test catches a mistaken comparison. This assumes well-formed records; production parsers need malformed-record handling.

Variation: add a 502 record and predict the ID list. Save the test and interpretation in weekly-logs/week-11.md. For a real mistake, append symptom, cause, check and regression to mistakes.md; don't invent an incident merely to fill the page.

Make cloud delivery explicit

CloudWatch organizes log events in streams inside groups. An app printing stdout does not automatically create cloud delivery. For this EC2 path use Docker's awslogs driver: the host daemon sends container output using its AWS credentials, normally the EC2 instance role. The app container need not access metadata for logging.

Learner AWS setup: create a log group named /week11/api in the chosen region, set retention to 7 days for this lab, and grant the host role CreateLogStream and PutLogEvents scoped to its streams. Precreating the group avoids granting CreateLogGroup to the runtime. See the driver's permissions section for ARN syntax and any additional permissions your settings require. Record group, role scope, region and retention in runbook.md. Ensure outbound HTTPS can reach CloudWatch.

On the host, from week11-runtime, create a candidate on loopback port 8001 with the same tested image and env file:

sudo docker run -d --name week11-cloudlogs \
  -p 127.0.0.1:8001:8000 --env-file .env \
  --log-driver awslogs \
  --log-opt awslogs-region=YOUR_REGION \
  --log-opt awslogs-group=/week11/api \
  --log-opt awslogs-stream=week11-v1 \
  week11-api:v1
curl -i http://127.0.0.1:8001/health

Replace YOUR_REGION before running. In the CloudWatch console inspect the stream and match the response's request ID. Or, from a laptop with AWS CLI and a read-authorized identity:

aws logs tail /week11/api --since 10m --region YOUR_REGION --format short

Record the matching event without secrets. Failed startup with an awslogs error can mean missing group, wrong region, denied action or unavailable endpoint. No events after startup can mean wrong stream/time range, log level or delivery trouble; verify locally, then the transport. Do not “solve” this by granting AdministratorAccess. Log delivery behavior can affect availability; understand the driver's blocking/buffering choices before using it for higher-load production.

Deployment succeeded, API returns 500

Check the release and readiness first. Find its event by request ID; compare to the last working version; inspect configuration names and dependency reachability. The fixture deliberately sanitizes unexpected error details, so its event alone cannot identify the underlying exception. For the rehearsal, FAIL_MODE is the known injected cause. A real backend needs safe internal error classification and restricted exception diagnostics, without prompts/keys/user documents in general logs.

Write one debugging flow in runbook.md, including “no cloud events” as a separate failure. The host candidate consumes additional resources; remove only that disposable candidate after capturing evidence: sudo docker rm -f week11-cloudlogs. The original week11-api remains. Next: rehearse a failed release and recovery locally before trusting cloud rollback.
