Week 11 · 04

Build an identifiable container

Build the learner Dockerfile and distinguish container binding from host publishing.

An image is a packaged filesystem and startup command. A container is a running instance of it. The host must know which port to forward to, and the process inside must listen on a reachable interface. EXPOSE is documentation; it does not publish a port.

A tiny build trace

Consider these Dockerfile instructions separately: WORKDIR /app sets later relative paths; COPY requirements.lock . copies from the build context, not from the Dockerfile's own directory. RUN python -m pip install --no-cache-dir -r requirements.lock changes the image during build. CMD ["uvicorn", "app:app", ...] defines runtime execution. In app:app, the first app is the Python filename without .py; the second is its FastAPI object. JSON array syntax avoids an extra shell and forwards signals to the server process.

A common failure: building from projects/deployment makes requirements.lock unreachable, because it is above that context. Another: listening on 127.0.0.1 inside the container makes Docker's forwarding unable to reach the app. The app binds 0.0.0.0 inside; the host publishes only loopback for the private lab.

Small bridge: base image, user and output buffering

FROM python:3.12-slim starts from an image containing Python and a small Linux userspace. ENV PYTHONUNBUFFERED=1 makes Python output appear promptly in logs. On this Debian-based image, RUN useradd --create-home worker creates a named account during the build; USER worker makes runtime execution use it. Installed packages and copied source must be readable by that user. A permission-denied write to /app is a filesystem issue: choose an intended writable data location instead of switching the service back to root. These are individual mechanisms; assemble your own Dockerfile next.

Implement the image

Start at the week root. Edit Dockerfile using its contract comments. Use Python 3.12 slim, install the lock, copy only fixture/app.py, set unbuffered output, create an unprivileged runtime user, and run Uvicorn on 8000 with access logging disabled (the fixture emits safe events). Read .dockerignore: it excludes secrets and generated files from build context. Do not add .env to an image layer. The tutorial lock includes test tools for convenience; a production runtime can later use a separately verified runtime-only lock.

cd /home/an10/code/notes-repo/cloud-devops/week-11
docker build -f projects/deployment/Dockerfile -t week11-api:v1 .
docker image inspect week11-api:v1 --format '{{.Config.User}}'
docker run --rm --name week11-local -p 127.0.0.1:8000:8000 \
  --env-file projects/deployment/.env.example week11-api:v1

The starter must fail to build before your implementation; “file with no instructions” (or “no build stage”) is expected. Docker daemon denial, network failure pulling Python, and dependency installation failure are infrastructure problems, not proof your code is wrong. For permission errors, diagnose your Engine installation; do not make the Docker socket world-writable.

In a second terminal, start at the same week root and run:

curl -i http://127.0.0.1:8000/health
curl -i http://127.0.0.1:8000/ready
curl -i http://127.0.0.1:8000/message
curl -i -H 'X-API-Key: local-rehearsal-only' http://127.0.0.1:8000/message

Expect 200, 200, 401, 200 respectively; health/message release is week11-v1. The shown key is public dummy data, never a real credential. Record image ID, user and observations in weekly-logs/week-11.md. Stop the foreground server with Ctrl-C; --rm removes only that lab container, not the image.

Hint for an import or connection failure

Check that /app/app.py exists in the image and WORKDIR is /app. “Could not import app” is a packaging/start-command problem. Connection refused with an exited container requires startup logs first; opening more security-group ports cannot fix a crashed process.

Independent variation: use host port 8001 while leaving container port 8000. Predict which URL works. Do not change app code. Next: move dummy configuration into an explicit secret lifecycle.
