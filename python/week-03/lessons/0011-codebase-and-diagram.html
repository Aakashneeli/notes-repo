Read before installing anything

From the weekly root read codebase-reading/SOURCE.md. The codebase-reading/sampleproject/ folder is an unmodified, commit-pinned snapshot of PyPA's small sample repository, including its MIT license. It is a packaging example, not a finished production service. Leave snapshot files unchanged. No external account, publishing or dependency installation is required for this reading exercise.

First read its README.md and LICENSE.txt for purpose and reuse terms. Find the script mapping in pyproject.toml. Then read src/sample/__init__.py, src/sample/simple.py, and tests/test_simple.py.

cd /home/an10/code/notes-repo/python/week-03
rg -n 'scripts|sample:main|dependencies' codebase-reading/sampleproject/pyproject.toml
PYTHONPATH=codebase-reading/sampleproject/src python -c 'from sample import main; main()'
PYTHONPATH=codebase-reading/sampleproject/src python -m unittest discover -s codebase-reading/sampleproject/tests -v

Expect the placeholder application message and one passing unittest. PYTHONPATH applies only to this command and points Python at the read-only snapshot's src; this avoids installing its packaging dependencies. Your own package uses normal installation from lesson 2. The upstream test imports add_one directly; the entrypoint main does not call add_one. A plausible-looking diagram joining them would be false.

Produce the reading deliverable

Read noxfile.py as test-session automation, test.yml as CI configuration and release.yml as publishing configuration. Read only; do not run release actions. Inspect .gitignore, package_data.dat and the empty tests/__init__.py: generated-file policy, bundled example data, and package marker respectively. Note absent service settings/Docker rather than inventing them.

Use templates/reading-note.md to fill codebase-reading/week-03.md. Include file/line evidence for entrypoint, modules, tests and config; trace one real execution; name one limitation; propose one pattern to borrow. Append a small docs experiment from RESOURCES.md. Your note must be in your words. One correct observation: packaging declares runtime dependencies, but the tiny tested function itself does not use all of them.

Make the module diagram yours

Read templates/module-diagram.drawio as a blank editable drawing with a prompt, then save a copy as projects/text-workbench/module-diagram.drawio. From the weekly root, create the learner copy without overwriting an earlier diagram:

cd /home/an10/code/notes-repo/python/week-03
cp --no-clobber templates/module-diagram.drawio projects/text-workbench/module-diagram.drawio

Use a locally installed draw.io desktop app, or the official diagrams.net editor with Device storage as an explicit learner choice. Open the copied file with File → Open from → Device; edit the diagram, then File → Save as, choose Device and the same project path. In the desktop app use File → Open and File → Save As. If a previous diagram exists, open it rather than replacing it. Do not upload private source or connect an account. If no editor is available, sketch nodes/arrows in the project README first and leave the editable-diagram requirement pending.

Draw your actual modules; arrow A → B means A imports/depends on B. Use differently labelled arrows for runtime data flow. Mark pure rules, effects and startup configuration. Trace file → service → core → Record → CLI stdout, and the separate logging path. Explain one alternative grouping and why you kept or changed the suggested boundaries. The blank template is not a completed diagram. Record the saved path in progress. Next: independent review and local Git evidence.
