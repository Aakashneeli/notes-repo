Week 03 · Pro Python · Lesson 08

Keep policy separate from effects

Make the workflow testable by passing the file reader in.

Practical low-level design

LLD here means deciding which small unit owns which rule. Core owns text rules; models own valid records; settings owns interpretation of external configuration; service coordinates a workflow; CLI owns terminal arguments and presentation. This is a proposed teaching skeleton, not proof that every program needs six modules. In your diagram, argue whether any boundaries should be combined.

A function is enough for a stateless transformation. A class earns its place when instances hold meaningful state or enforce a lifecycle. A TextManager class with one method and no state may simply add navigation. Conversely, a validated Config object usefully groups related values. Judge the interface by what a caller must know, not by how many classes exist.

Dependency direction

Read src/text_workbench/service.py. The supplied read_utf8 adapter calls Path.read_text with explicit UTF-8 encoding; it can raise file or decoding errors. process_file accepts a reader callable, defaulting to that adapter. A test can pass a fake returning text without creating a real file. Core must not import CLI or settings; otherwise testing a word count may unexpectedly depend on your shell.

Trace a smaller example: describe(load) calls load once → receives "abc" → calculates length 3 → returns "3 chars". The describe function does not know whether load read a file or returned a constant. Edit describe in ../../practice/exercises.py and run:

cd /home/an10/code/notes-repo/python/week-03/projects/text-workbench
uv run pytest ../../practice/test_exercises.py -k describe -q
Hint 1

Store the result of calling load in a local variable.

Explained answer
text = load()
return f"{len(text)} chars"

Calling load twice could read two different file versions. The supplied test records calls and requires exactly one.

Implement the workflow

Implement process_file according to its contract. Read once, check the raw text's character limit before normalization, compute metadata through core, validate a Record, emit one fixed INFO event named processed with safe count fields, and return the Record. Let file, decoding and size errors reach the CLI; there is no useful fallback result. Empty files are valid. An input exactly at the limit is allowed.

Read tests/test_service.py before running uv run pytest tests/test_service.py -q. tmp_path creates disposable real files; caplog captures LogRecords independently of JSON formatting. The fake-reader test proves orchestration in isolation; real-file tests prove the local adapter. Neither proves cloud storage or HTTP integration.

Our simple reader loads the whole file before checking the character limit. This is suitable for the bounded local lab, not a memory protection boundary for untrusted uploads. Large means 200,000 raw characters in the supplied test, not an unlimited stream. Record this tradeoff in the project README. Explain what becomes hard to test if core reads os.environ or opens files itself. Next: understand waiting without adding async complexity to this CLI.
