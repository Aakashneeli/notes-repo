Week 03 · Pro Python · Lesson 06

Load configuration once, explicitly

Turn environment strings into one validated settings object without hidden global reads.

A boundary with three stages

The shell environment is a mapping of names to strings. Our chosen flow is: CLI reads os.environ at startup → settings selects two names and converts the numeric value → Config validates → the service receives the object. Core functions receive explicit arguments and never search the environment. This lets two tests use different settings in the same process without depending on your shell.

.env.example documents safe example values; read it from the project directory. It contains no credentials. A file named .env has no magic effect in Python: our loader does not read it. Use command-scoped environment assignments for this lab. A larger app could use a dedicated settings library, but this week's small explicit loader makes precedence visible.

Hint 1

Use env.get for the missing-key default, int for conversion, then check the result.

Explained answer
value = int(env.get("LIMIT", "5"))
if value <= 0:
    raise ValueError("LIMIT must be positive")
return value

int raises ValueError for non-integer strings. The later branch handles syntactically valid but disallowed values. Catching every failure and silently returning 5 would disguise a configuration mistake.

Implement the real loader

Edit src/text_workbench/settings.py. Missing keys use Config defaults. TEXT_MAX_CHARS is converted with int; the Config strict integer therefore sees an integer. TEXT_LOG_LEVEL is exact uppercase. Ignore unrelated environment names; forbid unknown fields in Config itself. Never pass all os.environ into Config.

Run uv run pytest tests/test_models_settings.py -q. Expect all config/model checks to pass now. Diagnose a string-versus-int validation failure by tracing where conversion should have occurred; don't weaken strict output counts just to accept environment strings. Defaulting with env.get(...) or ... hides explicitly blank settings.
