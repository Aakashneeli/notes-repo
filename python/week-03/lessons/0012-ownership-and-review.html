Week 03 · Pro Python · Lesson 12

Demonstrate ownership after a delay

Finish through explanation, variation, reproducibility and deliberate local commits.

Four explanations without code open

Use plan/assessment.md and explain: why these modules; which functions are pure and which have effects; where configuration loads and why; what becomes hard to test if code moves into the wrong layer. Then open code and correct your explanation with concrete call paths. Record corrections in the weekly log. The diagram and README should agree with actual imports.

Commit only your intended work

From the repository root, inspect current work. This repo already contained untracked learning work before Week 3 was authored. Do not stage it all. Choose an unused branch name and review explicit paths:

cd /home/an10/code/notes-repo
git status --short
git switch -c learn/week-03-pro-python
git diff -- python/week-03

Untracked files do not appear in git diff; inspect them in your editor. Stage only files you intend to record (for example a completed core and its tests), then review the staged patch before committing:

git add python/week-03/projects/text-workbench/src/text_workbench/core.py python/week-03/projects/text-workbench/tests/test_core.py
git diff --cached --check
git diff --cached -- python/week-03
git status --short
git commit -m "Implement and test text normalization contracts"

Before committing, ensure the complete staged list contains only intended work; if others were already staged, pause and preserve them rather than bundling unrelated changes. Use your own accurate commit message. Subsequent commits should include the project manifest/lock, wrappers, models, settings, logging, docs and evidence when reviewed. No push, PR submission or remote changes are required. If the branch already exists, inspect it and use another unused name.

Reproduce the local package

From the project directory run the commands below. The optional output directory is generated output ignored by Git; do not overwrite an earlier artifact without inspecting it.

cd /home/an10/code/notes-repo/python/week-03/projects/text-workbench
uv sync --locked
uv run pytest -q
uv run ruff check .
uv run ruff format --check .
cd ../..
python maintenance/verify_workspace.py

The verifier checks local links, file-map coverage, HTML essentials and Python syntax, and runs only completed teaching examples. It reports starter status separately without marking learning. Read its source and VALIDATION.md for exact scope. Tutor verification never fills learner checkboxes.

Space retrieval and reduce hints

After roughly two days, use the review template: explain None/defaults, trace a config failure and predict an async ordering without notes. After roughly a week, implement a small variation independently in your own branch: add an optional output field for unique tokens, first deciding whether repeated normalized tokens count once. Update model, core, tests, README and diagram. This is a text-product variation, not an interview problem. Keep the original required contract compatible or document the deliberate version change.

Complete the reading note, module diagram, README failure examples and one real debugging writeup. Update progress with command outputs and commit IDs only when demonstrated. Ask the tutor to challenge one design decision, not generate your missing implementation. If something remains unclear, leave it pending and identify the smallest experiment that would resolve it.

Recall before moving on

Close the example. Explain the idea in your own words, then change one input and predict the result. Record help used and evidence in weekly-logs/week-03.md. Passing author checks is not proof of your learning.

Primary source: official documentation or original author. Read one relevant section, predict a tiny experiment, then test it. Ask your teacher about anything unclear; share your prediction, command and actual result.
