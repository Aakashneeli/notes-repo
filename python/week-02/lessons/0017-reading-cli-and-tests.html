Week 02 / Guided practice

Read every line of a command.

The project wrapper should not be mysterious supplied code. Read this smaller, fully working command first. It separates a simple rule from terminal input/output. Split the walkthrough into two passes: run the command, then read its tests.

import argparse
import sys


def greeting(name: str) -> str:
    if not name.strip():
        raise ValueError("name must not be blank")
    return f"Hello, {name.strip()}"


def main() -> int:
    parser = argparse.ArgumentParser(description="Greet one person")
    parser.add_argument("name")
    args = parser.parse_args()
    try:
        message = greeting(args.name)
    except ValueError as error:
        print(f"error: {error}", file=sys.stderr)
        return 2
    print(message)
    return 0


if __name__ == "__main__":
    raise SystemExit(main())

Pass 1 · Follow one command

cd /home/an10/code/notes-repo/python/week-02
python practice/worked-greeting/greet.py "  Asha  "

Expect Hello, Asha. The shell keeps the quoted text as one argument. Python executes the file. The final name guard calls main because this file is being run directly. parse_args reads the one required name and stores it on args. greeting checks/cleans that value and returns a string. main prints it and returns 0; SystemExit turns that into the process exit status.

Why each piece exists

import argparse makes a standard-library module available. ArgumentParser creates a parser object. The methods add_argument and parse_args declare and read the command’s inputs. args.name accesses the parsed argument by its declared name. Missing a required argument makes argparse show usage and exit with an error before your function is called.

name: str and -> str are type hints for readers/tools. They do not automatically reject every wrong Python value. The explicit if checks the input condition we care about. The core function returns data and raises ValueError for invalid input; it does not know about the terminal. This makes it straightforward to call in a test or reuse elsewhere.

except ValueError as error binds the raised exception to error. The wrapper prints the diagnostic to stderr and returns 2. A typo such as an unknown Python name should not be swallowed by this handler—it is a different error type that needs debugging. The name guard prevents command parsing when another module imports greeting.

See normal output and diagnostics separately

python practice/worked-greeting/greet.py "   " > practice/greeting-output.txt 2> practice/greeting-error.txt
echo $?
cat practice/greeting-output.txt
cat practice/greeting-error.txt
Expected observations

Exit status is 2. The stdout file is empty. The stderr file contains error: name must not be blank. 2> redirects the diagnostic channel; plain > redirects the normal output channel. Run echo $? immediately after the program because the next command changes that value.

Now run python practice/worked-greeting/greet.py --help and then run it with no name argument. Compare the parser’s help/usage behavior with the explicit blank-name validation. An omitted argument and an argument containing only spaces fail in different places.

Pass 2 · What a test actually proves

python practice/worked-greeting/test_greet.py

Two checks should pass. Open test_greet.py. assertEqual compares the returned value with an expected value; assertRaises states that a particular failure is expected. Test setup creates input, the call exercises behavior, and an assertion compares it with the contract. Temporarily remove strip() from the returned greeting, run the tests, observe the first failure, then restore the code and rerun.

The toolbox uses pytest for the same idea. Its plain assert actual == expected checks equality. with pytest.raises(ValueError): expects that exception inside the indented block. tmp_path is a pytest fixture that supplies a new temporary directory per test. The checker creates files there so tests do not depend on your personal documents. @pytest.mark.parametrize repeats a case over different supplied inputs; you only need to read its case values this week.

cd projects/week-02-toolbox
uv run pytest tests/test_file_counter.py -q
uv run pytest tests/test_file_counter.py -k empty -vv

The first command runs a file; the second narrows to test names matching empty and prints more detail. A failure in your unfinished function is expected. Do not change the expected number until you can show the test conflicts with the written contract. A regression test is a case added to keep a previously fixed bug from returning.

In the worked unittest file, class GreetingTests(unittest.TestCase) groups checks and inherits the runner’s assertion helpers. Each test_... method is one check; the runner supplies self, the test object, so self.assertEqual can report a failure. You can read these two tests without learning class design this week. Your project’s pytest functions avoid this class wrapper.

Map the example onto your toolbox

greeting corresponds to a core function such as count_files. The toolbox main adds Path conversion or file reading because its inputs are files. CLI tests additionally start a subprocess so they can inspect stdout, stderr and the exit status; function tests call the core directly. Both matter: the core may be correct while argument parsing or output behavior is wrong.

Explain-back before you leave

Why can tests import greeting without asking for a terminal argument? Because the name guard does not call main during import. Why does the empty-name error go to stderr? It is a diagnostic, separate from the useful result. Why return from the core instead of print? The caller can inspect/reuse the value and choose presentation.
