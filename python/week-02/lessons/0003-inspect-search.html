The idea

Inspect a small file with cat; browse a long one with less. Use head and tail for the beginning or end. In less, /ERROR searches, n advances, and q quits. rg searches content; find selects filesystem entries. A pipe passes standard output to the next command’s standard input.

Read the primary source: ripgrep: maintainer’s guide · GNU Coreutils manual · GNU Findutils manual

Build the mental model

Follow the text, not just the command names

A program normally reads input from standard input and writes results to standard output. The terminal connects these channels to your keyboard/screen unless you redirect them. A pipe, |, connects the first command’s output to the next command’s input. It passes text; it does not pass filenames automatically.

rg "ERROR" projects/week-02-toolbox/data/app.log | tail -n 1
StageInputOutput
rgThe five-line fileThree matching lines, in file order
tailThose three lines from the pipeINFO previous ERROR recovered

That final line is correct for the command you asked for: it contains ERROR. It is not an ERROR-level event. Precise questions matter. rg '^ERROR ' ... asks for lines starting with the level token. You will later encode that distinction in Python.

Search names and search contents separately

rg --files src lists searchable filenames. rg "def " src reads their contents and finds function definitions. find data -type f -name "*.json" walks directory entries and selects regular files whose names match the pattern. Quote "*.json" so find receives the pattern instead of the shell expanding it first. ripgrep’s ignore rules are helpful for source search but can hide entries from a filesystem inventory.

Write output deliberately

> replaces a destination; >> appends. Do not use the source file as the destination. The shell opens a redirection before the program runs, so the original may be truncated before the program reads it. Test on a throwaway file:

printf 'first\n' > practice/output-demo.txt
printf 'second\n' >> practice/output-demo.txt
cat practice/output-demo.txt

Expect first and second on separate lines. Here \n tells printf to write a newline. For help, use head --help, rg --help, or man less if manual pages are installed. Ctrl+C stops a foreground command; q exits less. These are different controls for different programs.

Try it yourself

cd /home/an10/code/notes-repo/python/week-02
cat projects/week-02-toolbox/data/app.log
less projects/week-02-toolbox/data/app.log
head -n 2 projects/week-02-toolbox/data/app.log
tail -n 2 projects/week-02-toolbox/data/app.log
rg -n "ERROR" projects/week-02-toolbox/data/app.log
rg --files projects/week-02-toolbox/src
find projects/week-02-toolbox/data -type f -name "*.json"
rg "ERROR" projects/week-02-toolbox/data/app.log | head -n 1

Run tail -f projects/week-02-toolbox/data/app.log, then press Ctrl+C to stop following. It waits for appended lines; it is not stuck. Find a term with no matches using rg, then run echo $? immediately.

Expected result · open after your attempt

The text ERROR appears on lines 2, 4, and 5. Line 5 is an INFO event whose message mentions ERROR; searching for text is not the same as parsing a log level. The pipe shows the first error line only. The JSON search finds example.json and invalid.json. rg with no matches returns status 1; an execution error is a different case. rg normally skips hidden and ignored files, so it is not a complete filesystem inventory.

Check your model

Which searches file contents?

For actual ERROR-level events in this sample format, try rg -n '^ERROR ' projects/week-02-toolbox/data/app.log. The ^ anchors the match at the start of the line. This gives lines 2 and 4, excluding the INFO message on line 5.
