The idea

Git records project history locally; GitHub hosts repositories and collaboration. Your working tree is what you edit. The staging area selects the next snapshot. A commit records that staged snapshot with a message and parent history. After staging, later edits remain unstaged until you add them again. An ignored file already tracked stays tracked.

Read the primary source: Pro Git: recording changes

Build the mental model

A three-version trace

Imagine notes.txt is already committed containing one. You edit it to two, run git add notes.txt, then edit it again to three without adding. You now have three versions:

LocationContentHow to inspect it
Last commitonegit show HEAD:notes.txt
Staging areatwogit show :notes.txt
Working treethreecat notes.txt

git diff compares the working tree with the staging area: two → three. git diff --cached compares the staging area with the last commit: one → two. If you commit now, the commit contains two. It does not silently include the later edit to three. This lets you choose exactly which content to record.

Understand what status is telling you

git status is the beginner-friendly explanation. git status --short uses two columns: the first describes the index versus HEAD, the second the working tree versus the index. ?? means untracked. A tracked file showing MM has both staged and unstaged changes. Untracked files do not appear in ordinary git diff until you add them.

A commit message should help your future self understand the reason for the snapshot: “Exclude symlinks from direct file count” is useful; “changes” is not. Inspect the actual diff instead of trusting a filename list. A good commit is a coherent step, not a screenshot of everything in your directory.

Recover from staging the wrong thing

After a repository has a commit, git restore --staged README.md removes its staged changes from the next snapshot while preserving your edits on disk. That is different from git restore README.md, which can discard working-tree changes. Use the explicit --staged form for this exercise. To check what a commit changed, use git show --stat and then git show.

Try it yourself

Keep Git exercises in the toolbox, separate from the parent notes repository. The following initialization is a learner task; no history has been fabricated for you.

cd /home/an10/code/notes-repo/python/week-02/projects/week-02-toolbox
git init -b main
git rev-parse --show-toplevel
git status --short
git add README.md .gitignore .env.example pyproject.toml src tests data
git diff --cached --stat
git diff --cached
git commit -m "Set up week two toolbox exercises"

If Git asks for identity, set your own git config user.name "Your Name" and git config user.email "your chosen email" here, then retry. These are repository-local settings. Now change the README’s ownership note, stage only README.md, inspect git diff --cached, and commit with a message explaining the change.
