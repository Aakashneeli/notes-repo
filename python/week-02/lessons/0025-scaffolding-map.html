Week 02 / Foundation

Understand the supplied feedback tools

Read one step, try it, then pause. These are completed teaching examples; proposed repairs and variations are learner exercises.

Scaffolding connects your code to inputs and checks. You own the function behavior, while the supplied files make it possible to run a command and compare its result. You should be able to explain the connection before trusting a green test.

In TOML, brackets introduce tables and quoted names are strings. The pytest table's testpaths = ["tests"] tells the runner where to look. The build backend installs the src package so module imports and console commands work. Standard-library imports such as json need no additional runtime dependency. Lesson 07 traces these configuration choices; lesson 17 traces main line by line.

The beginner checker, one step at a time

Read check.py. Its imports have specific jobs: argparse reads the group and optional --file; Path handles the filename; importlib.util loads that selected Python file; json identifies the expected parse exception; tempfile supplies disposable file fixtures; sys sends setup diagnostics to stderr.

main parses arguments. The default exercises path comes from Path(__file__).with_name("exercises.py"), so it is beside the checker, independent of your current directory. A relative --file argument is still relative to your shell directory. The module specification tells Python what file to load; module_from_spec creates the module object and exec_module executes its definitions. Load only your own exercise file: loading Python executes its top-level code.

cases(ex) builds tuples of group, label and a callable check. Its nested case helper appends each tuple. A lambda is a short function: it delays the exercise call until the runner invokes it. Defaults such as lambda n=count: ... capture that iteration's input, preventing every later check from seeing only the final loop value. You need to read this here, not reproduce the harness.

same compares both type and value: True should not silently pass for integer 1. Some named checks additionally verify the original list is unchanged or expect a particular exception. TemporaryDirectory creates disposable fixtures and removes them when the with block exits.

The runner selects the requested group, calls each check, reports TODO for NotImplementedError, FIX for other failures, and PASS otherwise. It continues so you can see several cases. Exit 0 means every selected check passed; 1 means at least one did not; 2 means the exercise could not be loaded. This broad catch is appropriate for a diagnostic test runner; it is not a model for returning fake success in your project.

Read one subprocess test

In test_cli.py, Path(__file__).resolve().parents[1] locates the project root from the test file. sys.executable uses the same interpreter as the test runner. subprocess.run gets a list of arguments (no shell parsing), sets cwd, captures stdout/stderr, decodes text, and imposes a 10-second timeout. Assertions inspect returncode and output. A pure-function test cannot prove that a wrapper prints to the correct channel; the subprocess check can.

A feedback exercise

Start at the course root. Run the strings group and predict its current result:

python practice/foundation-drills/check.py strings
echo $?
Hint 1

Inspect whether the two string functions still raise NotImplementedError.

Hint 2

Each function has two cases, so four TODO results are expected before implementation.

Explained answer · after your attempt

Fresh starter: four TODO lines, 0/4 checks passed, shell status 1. After both functions are correct: four PASS lines and status 0. If you have already implemented one, predict from your current file instead. This is behavior feedback, not a mastery score.

Recall and variation

Explain why a test can fail even though setup succeeded. Run the checker with a nonexistent --file path and predict the exit code. Expected: setup diagnostic and exit 2. Then explain the difference between that and an unfinished function.
