The idea

A branch names a line of work. Switching changes the checked-out branch; merging combines histories. A fast-forward can simply move the branch pointer. A conflict requires you to choose the intended content; Git cannot decide the meaning of overlapping edits. Remotes are named repository locations. Fetch downloads history; pull fetches and integrates; push sends local commits. A PR proposes a branch change for review.

Read the primary source: Pro Git: branching and merging · Pro Git: remotes · GitHub: creating a pull request

Build the mental model

Picture the history before running merge

Before feature work:  A ← main

After feature work:   A ─ B ← feat/example
                      ↑
                     main

After fast-forward:   A ─ B ← main, feat/example

The feature branch begins at the current commit; it is not a separate copy of the entire repository that you manually paste back. In this simple case, main has no unique new commits, so merge can move main to B. If both branches have unique commits, Git may create a merge commit with two parents. A merge is not required to delete the feature branch; those are separate actions.

Conflict resolution is a content decision

<<<<<<< HEAD
Run the tool from the project root.
=======
Run the command inside the toolbox folder.
>>>>>>> docs/usage

These markers show competing content from the current branch and the branch being merged. Read both and replace the entire marked region with the intended final text, perhaps “Run the tool inside projects/week-01-toolbox.” Do not leave the markers in the file. Save, inspect git diff, stage the resolved file and commit. If you do not understand which behavior is right, pause and explain the two alternatives.

When reviewing a Python conflict, a syntactically valid merge can still be behaviorally wrong. Run the relevant checks after resolving it. Start branch/merge exercises with a clean working tree so that unrelated edits do not complicate the result.

Know which name refers to which place

NameMeaning
mainA local branch
originA conventional remote name; not a special server
origin/mainYour local record of the remote branch at the most recent fetch
HEADThe current checked-out position, normally attached to a branch

The remote may advance after your last fetch; origin/main is not a live view of the server. A push refusal often means there is history to integrate, not that Git is broken. The local remote lab makes this visible without authentication or publishing. The conflict lab gives you a controlled overlap to resolve yourself.

For each later script, repeat this workflow with feat/file-counter, feat/json-pretty, and feat/log-filter. Merge only after its checks pass. Rehearse clone/push/pull using the local remote lab. Then use the PR template for a self-review. GitHub steps are included for when you have your own remote.

Expected result · open after your attempt

main contains your usage change after the merge. A commit is still local until pushed. If merge reports a conflict: run git status, open the listed file, replace conflict markers with the intended combined content, git add the file, then git commit. To abandon an in-progress merge, git merge --abort returns to the pre-merge state when Git can restore it; start merges with a clean working tree.
