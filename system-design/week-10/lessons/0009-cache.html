Week 10 / Lesson 09

Design cache and rate-limit behavior

Specify tenant-safe keys, staleness and atomic quotas.

A cache trades repeated work for the risk of serving stale data. Cache-aside means: read the cache; on a miss read the source; store the result for a bounded time; return it. It should not become the authority for whether a user may access a document.

Trace a miss, hit and stale hit

t=0: tenant red, corpus v1, query Q → miss → retrieve → store for 30 s
t=2: same authorized key → hit → reuse retrieval result
t=3: corpus changes to v2 → different key → miss
t=4: tenant blue, same query → different key → miss

TTL (time to live) limits how long an entry remains, but does not make it immediately fresh. A permission revocation can require immediate invalidation or fresh authorization at use. A retrieval cache key may need tenant, authorization scope, corpus version, embedding/retrieval settings and query. An answer cache additionally depends on prompt/model versions. Do not cache only the question: identical words can refer to different private corpora.

Concurrent misses for one popular key can stampede the database. Consider a bounded single-flight refresh or stale-serving policy only when privacy/freshness requirements allow it. Cache outage may fall back to the source, but bound that load. Unlimited fallback can take down the primary store.

Rate limiting is a different policy

A limit protects capacity or budget by rejecting excess work. For a toy fixed window of 10 requests per authenticated tenant per minute, increment a Redis counter keyed by tenant and window; allow counts 1–10, reject 11+. Return 429 with retry guidance. Increment and expiry must be atomic together (a transaction or script), or a crash between them can leave a permanent counter. Fixed windows allow bursts near the boundary; stricter smoothing is a separate design choice. Never trust a tenant string supplied in the request body to allocate quota.

When Redis is down, choose deliberately: fail closed protects an expensive model budget but rejects legitimate requests; fail open preserves availability but risks overload. A bounded per-process fallback is approximate across replicas. State that limit rather than claiming distributed enforcement.
