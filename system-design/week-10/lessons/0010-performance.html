Week 10 / Lesson 10

Measure before choosing an optimization

Run a controlled latency experiment and separate waiting from work.

Latency is elapsed time per request; throughput is completed requests per second. A percentile describes a sorted sample: p95 is a value at or above 95% of observations under the chosen convention. Twenty requests give a rough teaching sample, not a trustworthy production tail estimate. Count failures and include their durations.

Predict the experiment

Read experiment.py. It uses the fixture's 20 ms retrieval wait and 10 ms model wait. Cooperative mode uses asyncio.sleep; blocking mode calls time.sleep inside async work. Four tasks can share waiting time only when they yield the event loop. async in a function header alone does not make synchronous I/O nonblocking.

The harness uses a semaphore, a gate with a fixed number of slots. All jobs are submitted as one burst; queued jobs wait for a slot. latency_ms includes that wait; service_ms starts after the slot is acquired. Every tenth request deliberately fails during retrieval, giving 10% errors for count 20. gather schedules work; it does not invent extra CPU cores. The result reports nearest-rank p50/p95, wall-time throughput and every raw row.

Run the roadmap experiment locally

# Start: system-design/week-10
python projects/architecture-review/experiment.py --mode cooperative --concurrency 1 --count 20
python projects/architecture-review/experiment.py --mode cooperative --concurrency 4 --count 20
python projects/architecture-review/experiment.py --mode blocking --concurrency 4 --count 20

Run each configuration three times, with other heavy tasks quiet. Expect cooperative concurrency 4 to improve throughput over 1; blocking mode should lose much of that improvement. Do not require an exact timing threshold on a busy machine. If results disagree, keep them and inspect scheduling, CPU load and measurement definitions. The CLI bounds count/concurrency to avoid an accidental huge run.

Fill performance.md with command, Python/hardware context, repetitions, p50/p95, throughput, errors and a bottleneck hypothesis. Other levers and their costs

An index helps a database locate/order records for a query but adds storage and write maintenance. For a tenant's recent documents, a candidate index on (tenant_id, created_at, id) can support the filter and stable ordering; check the actual query plan and data size before adopting it. Use your existing index lesson if reading plans is a gap.

SELECT id, created_at FROM documents
WHERE tenant_id = :tenant
  AND (created_at, id) < (:last_time, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;

This is parameterized illustrative PostgreSQL, not a command against an existing DB. Pagination caps response work. The ID breaks equal-time ties; a cursor page continues after the last tuple. Offset pages may become expensive and shift under concurrent writes. Define consistency expectations and retain authorization filters on every page.

Work a tiny page by hand: authorized rows in descending order are (10:00, 7), (10:00, 6), (09:59, 5). With a page size of two, page 1 returns IDs 7 and 6; its last tuple is (10:00, 6). Page 2 selects tuples strictly smaller than that pair, so it returns ID 5. If you compared only time, a third row at 10:00 could be skipped. In performance.md, predict the pages after adding row (10:00, 4). Check: page 1 is still 7,6; page 2 is 4,5. Keep the tenant condition on both pages. This is a query-reasoning check, not a measured PostgreSQL plan.

Embedding batching amortizes request overhead but increases memory, latency for a partially filled batch and the scope of a failed request. Bound by both item count and token/provider limits; preserve each chunk's ID so results cannot attach to the wrong text. Async I/O helps waits overlap; CPU-heavy parsing may need worker processes. Wrapping blocking I/O in a thread can help, but cancellation does not guarantee the underlying thread stops.

Batching trace: with four chunks and a fictional fixed overhead of 40 ms per call plus 5 ms per chunk, four sequential one-chunk calls take 4×45 = 180 ms. Two two-chunk calls take 2×50 = 100 ms. One four-chunk call takes 60 ms, but all four wait for that call and a failed batch affects all four. In your note, vary the batch size to three: batches of three and one total 55+45 = 100 ms in this toy model. Real provider measurements may differ. An index likewise needs evidence: on a tiny table a sequential scan may win, so do not call an unused index a bug without reading the plan and workload.

Guided observation: identify one waiting bottleneck from your measured modes. Independent variation: change concurrency to 2 and predict the trend before running. In the performance note choose one quick win and one optimization to defer with reasons. This experiment demonstrates in-process scheduling, not HTTP load capacity, real vector latency or a cloud sizing result. Your real API needs a later bounded test against a local test instance and safe data. Continue to Lesson 11.
