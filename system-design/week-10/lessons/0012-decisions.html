Week 10 / Lesson 12

Write decisions an operator can use

Produce four reasoned ADRs, an actionable runbook and a reviewable change description.

An architecture decision record (ADR) preserves a consequential choice with its context and tradeoffs. “Use tool X because it scales” is not enough: how much load, which constraint, and what would make you change? A runbook instead tells someone what to do during a specific symptom. A PR description tells a reviewer what behavior changed and how it was checked.

Worked miniature decision

Context: a small library's title catalog changes once daily and has one local operator. Decision: keep a single relational database; no separate search service yet. Alternative: a dedicated search system adds richer ranking but operational work. Consequence: modest search features and simpler backups. Revisit: a measured relevance failure or query latency exceeding an agreed target. This example connects a choice to constraints; it is not your vector-store ADR.

Use the ADR template to understand each heading. The four learner files already contain that structure: vector DB, queue, model provider, and deployment. Edit these directly; do not create duplicate decisions from the template.

Lab: four choices, four arguments

Start at system-design/week-10. Fill each ADR using your actual/proposed architecture and measured constraints. Vector DB: filters, persistence, backup and fit with existing Postgres versus a separate store. Queue: failure semantics, retry/dead-job inspection and worker ecosystem. Model provider: privacy, quality, latency, quotas, cost and fallback compatibility. Deployment: operator effort, isolation, persistence, recovery and budget. This is a design choice, not permission to deploy. Use the roadmap's no-usable-GPU and roughly $20/month cloud context as constraints, not a verified price quote.

For each, compare at least two plausible alternatives on the same workload; identify one downside of the chosen option and one benefit of the rejected option. Record assumptions that lack evidence and a measurable revisit trigger. If setup is missing, status remains proposed; do not invent operational experience. Read the book/resource annotations in RESOURCES and take one focused note in codebase-reading/reading-log.md. The source books are optional support; no purchase is needed to complete these explanations.

Hint — replace a vague justification

Instead of “Redis is fast,” ask: does my chosen queue library provide the retry visibility and recovery semantics I need, can I operate it, and what happens if Redis loses data? Name the durability assumption explicitly.

Finish the runbook and PR note

Revisit projects/architecture-review/runbook.md. For a latency spike, begin with time window, request volume, error rate and latency percentiles; correlate a slow request ID; inspect step durations, queue depth/age and recent changes. Distinguish a slow dependency from event-loop blocking. List bounded mitigation, verification and rollback. Do a tabletop rehearsal with the experiment's blocking mode; record what evidence would separate competing hypotheses.

Fill pr-description.md with the trigger, before/after behavior, tests and limitations of your instrumentation change. No PR is posted. Then, from the weekly root, inspect git diff -- projects/architecture-review/instrumentation.py and git status --short. New files appear in status but not the ordinary diff until tracked. Review exact paths before staging; never add secrets or ignored captures blindly.

Evidence: four ADRs with alternatives and consequences, a rehearsed runbook, and a concise PR note. Variation: halve the permitted operating budget or forbid prompt export. Identify which decision changes and which stays. Continue to the final review.
