Week 10 / Lesson 13

Prove ownership after the hints fade

Complete an independent implementation, debugging and explain-back review.

Author validation proves the teaching files behave as described. It does not prove you can design, debug or explain the system. Your completion evidence must come from independent attempts, including a change that was not shown in a worked example.

Run the local gates

# Start: system-design/week-10
python -m unittest discover -s practice -p test_exercises.py -v
python -m unittest discover -s projects/architecture-review/tests -v
python maintenance/validate.py

The first two require your implementations. The last checks supplied links, map entries, syntax, diagram structure and completed examples; it does not certify your decisions. Read VALIDATION to separate tutor checks from learner work. Do not remove meaningful assertions to turn the suite green.

Exercise a failure

In your own implementation, temporarily remove tenant/version separation from a cache-key experiment or force all observed requests to share one ID. Predict which test should fail, run it, explain the failure, then restore the correct implementation using your editor. Record actual output in mistakes.md. If the test stays green, improve it before claiming coverage. Do not introduce a fault into the supplied instructor examples.

Four source explain-backs

  1. What happens if the vector DB is slow or unavailable? Trace the deadline, response, safe fallback, logging and recovery; distinguish absence of evidence from empty retrieval.
  2. What should be retried and what should not? Include a read timeout, authorization failure and a side effect whose response was lost.
  3. Where are the trust boundaries? Use your data-flow diagram to locate uploaded text, authenticated identity, provider exports, tool execution and telemetry.
  4. What is the first thing you inspect when production latency spikes? Begin with scope/time window, latency/error/traffic metrics, then one correlated trace and a falsifiable hypothesis.

Answer without reading these lessons, then check against your evidence and the review card. Record assistance honestly in weekly-logs/week-10.md. Use the review template for another dated attempt; append to the log rather than replacing the previous one.

Commit a reviewable slice locally

From the weekly root, inspect status and the specific files you changed. Stage only your completed instrumentation file, its related evidence note and any new regression test; example:

git add projects/architecture-review/instrumentation.py projects/architecture-review/observability.md
git diff --cached --stat
git diff --cached
git commit -m "Add request-correlated AI event logging"

These are learner actions; the tutor does not commit for you. If other work is already staged, inspect it and choose your intended scope before committing. A commit is evidence of a change, not mastery; record its hash and explain what it proves. Nothing here pushes or publishes.

Return after a delay

At your next session, recall retry rules and redraw one view before opening notes. Two or three days later, use a new tenant/corpus version and one different failure to test your design. Around a week later, explain the whole ask path and defend one ADR to a skeptical reviewer. Flexible pacing is fine; the delay and reduced hints matter more than a calendar streak.

Use assessment as the completion gate, then update plan/progress.md with links to your own outputs. Mark real-backend integration pending until demonstrated. The tutor adds a numbered learning record only when your attempt establishes a nontrivial insight or corrected misconception; no empty records folder is required.

If you want practitioner feedback, the optional community in RESOURCES.md is a learner choice. Share a sanitized question and diagram only after reviewing what leaves your machine; no posting is performed for you. Ask the tutor to examine your reasoning, test results or one failed prediction.

Files at this step

From the weekly root, use these exact relative paths. Folders group the following roles; you do not need to memorize the full tree. Supplied tests/examples are infrastructure; implementation files and evidence notes belong to you.

  • plan/assessment.md — Read and demonstrate. Independent completion criteria and integration gates.
  • weekly-logs/mistakes.md — Append. Actual failures, diagnosis and regression checks.

  • reference/review-card.html — Read after recall. Compact failure/security/performance recall aid.
  • maintenance/validate.py — Run; tutor maintains. Static navigation/map/diagram/syntax and instructor checks; not assessment.
  • maintenance/test_infrastructure.py — Read/run; tutor maintains. Completed examples/harness tests plus event-check sensitivity; no project solution.
  • maintenance/browser-check.cjs — Optional author run. Headless Chromium layout check; requires externally available Playwright.
  • maintenance/author-results.md — Read; tutor-maintained. Author experiment observations, deliberately separate from learner records.
  • VALIDATION.md — Read; tutor-maintained. Precisely what was tested and remaining limits.
