Week 05 / lesson 14

Prove ownership after the hints close

Collect independent evidence and leave a reproducible project.

The material is ready when its mechanisms are taught and checked. Your learning is demonstrated when you can implement, test, debug, explain and vary them independently. Reading every lesson or passing a supplied example test does not complete this week.

Recall before reopening

Use templates/review.md fields in weekly-logs/week-05.md. Close notes and answer the source's four questions: Why these tables/relationships? What happens when two writes overlap? What query does this endpoint execute? What breaks when an index or constraint is removed? Include a concrete row/transaction example for each. Then compare with your actual code, diagram and output.

Revisit after roughly one, three and seven days; the intervals are flexible. Interleave one SQL prediction with one API failure diagnosis. If an explanation depends on seeing the answer, record that and retry a smaller variation later. Ask your tutor to challenge an explanation or provide one hint, not finish the repository.

Run the right checks

Starting at the weekly root, read VALIDATION.md for what the author actually verified and maintenance/verify_workspace.py for its limited local-link/file-map audit. Run:

python maintenance/verify_workspace.py
uv run pytest practice/test_examples.py -q
uv run pytest practice/test_exercises.py -q
source practice/local.env.example
uv run pytest practice/test_postgres.py -q
uv run pytest projects/task-api/tests -q

Passing maintenance checks proves navigation and syntax checks only. Passing instructor examples proves supplied mechanisms in their environment. Passing your project suite supplies behavioral evidence, still supplemented by manual restart, concurrency, diagram and explain-back evidence. Leave infrastructure defects, expected starter failures and independent learner success distinct.

Use assessment.md as the completion checklist and coverage.md to find evidence for every requirement. Update plan/progress.md with specific links, not “done because tests green.” Confirm all twenty Q labels contain your queries and observations. Fill the project's README run instructions and actual migration/index/relationship decisions. Keep unfinished deliverables visibly pending.

Review changes before a local commit

From the weekly root run:

git status --short
git diff -- projects/task-api/models.py projects/task-api/repository.py
git diff --check

Paths are relative to your current directory. An untracked file won't appear in normal git diff; inspect it directly before staging. Select only the files you intend to commit, for example git add -- projects/task-api/models.py projects/task-api/repository.py, then git diff --cached. Check the staged file list with git diff --cached --name-only; existing staged changes may belong to other work. If the complete staged set is intentional, make your own local commit and record its ID. This lesson does not require push, PR creation or publishing.

Migration source and learner notes belong in Git; .local database storage, .venv, caches and real credentials do not. .gitignore does not remove a secret already tracked. If you notice one, stop and get help handling the actual exposure instead of merely adding another ignore rule.

A small independent variation

Add an optional due_date to your own project without copying an implementation: choose API validation, model column, migration for existing rows and tests. Predict whether absent old values remain valid. Make it work on both a fresh schema and the current dev schema, retaining existing tasks. Explain the change after closing the files. This is a transfer assessment, not a new week or a provided finished feature.

Hint only if blocked

Start with the stored meaning and old-row policy, then schema transition, then input/output behavior. A date is not arbitrary text; use the relevant Python/database date types and validate boundary cases.

Check what counts as success

An existing row with no due date survives migration, invalid date input is rejected, and your changed API still passes old behavior checks. You can explain how absent differs from explicit clearing if your PATCH contract permits it.

For optional human perspective, use the communities in RESOURCES.md to ask a narrowly scoped, sanitized design question yourself. No external action is required for completion. Finish by choosing your next retrieval date and naming any unresolved gap honestly.

Primary reading: official documentation for this mechanism. Read after the worked example; the lesson supplies the reasoning you need to begin. Consult the command reference when returning after a break.

Ask your tutor a follow-up whenever a prediction, error or line of code remains unclear. Bring your attempted explanation and observed output.
