Measure an index's effect

Read a basic query plan and justify one project index.

An index is an extra structure that helps locate matching rows. It can reduce work for selective filters, but consumes storage and adds maintenance to writes. It does not usually change which rows a correct SELECT returns. A unique constraint protects correctness; its supporting index also aids lookup. Removing an ordinary performance index should slow some operations rather than permit invalid data.

Use enough rows to observe a choice

From the weekly root read practice/index-lab.sql. It creates 50,000 connection-local measurements with batch values 0–999. generate_series supplies integers; g % 1000 repeats batch labels, giving 50 rows with batch 42. Generated rows are experimental data, not learner observations. ANALYZE gathers planner statistics. Run:

psql "$W5_PSQL_URL" -X -f practice/index-lab.sql

The first plan typically uses Seq Scan, reading the table and filtering out most rows. After CREATE INDEX the second typically uses a Bitmap Index Scan plus Bitmap Heap Scan, or another index-based path. The count remains 50. Small tables or broad filters can still favor a sequential scan; don't disable sequential scans to manufacture evidence.

Read the plan from its working nodes upward

Seq Scan on measurements
  (cost=0.00..847.00 rows=50 width=8)
  (actual time=... rows=50 loops=1)
  Filter: (batch = 42)
  Rows Removed by Filter: 49950

This is an illustrative shape, not exact timing output. cost is a planner estimate in internal units, not milliseconds. Estimated rows help choose a plan; actual rows report execution. With loops greater than one, actual per-loop figures need careful interpretation. Buffers describes block activity such as shared hits/reads; a hit still involves work. Don't compare a cold first run with a warm second run as if the index alone caused every timing difference. Repeat both conditions on disposable data and compare plan shape and rows as well as time.

EXPLAIN estimates without executing; EXPLAIN ANALYZE actually runs the statement. This lab uses SELECT. Running ANALYZE on DELETE would delete rows unless contained in a deliberately rolled-back transaction. Never treat it as a harmless preview of a write.

Choose for your actual API

List filter WHERE done = ... ORDER BY id LIMIT ... suggests considering an index on (done,id). A boolean alone can have poor selectivity when half the table matches, and no index is always best. The existing unique title constraint already gives an index for exact title matches. Ordinary B-tree title indexing does not generally speed arbitrary substring LIKE '%term%'. Do not claim “all searches are faster.”

First hint

If PostgreSQL ignores your index on three rows, ask how many pages it must read anyway. Increase only disposable experiment data before deciding the index is broken.
