Week 05 / lesson 04

Make one valid write

Use keys and constraints to keep invalid rows out of storage.

API validation gives callers useful feedback, but scripts and other services can bypass it. Database constraints protect all writers. A primary key identifies a row uniquely and cannot be NULL. A foreign key requires a non-NULL reference to identify an existing parent. A unique constraint prevents duplicate values; a NOT NULL constraint forbids absence; a CHECK rejects a false condition. A CHECK alone does not reject unknown, so combine it with NOT NULL when absence is invalid.

In seed.sql, article id is a primary key and author_id references authors.id. The nullable author_id permits an unassigned draft. A title is required and nonblank. A Python dictionary key isn't a database foreign key; it doesn't make the server enforce any relationship.

Trace one write

At the weekly root start an interactive connection and load temporary samples:

psql "$W5_PSQL_URL" -X
\i practice/seed.sql
BEGIN;
INSERT INTO articles (id,author_id,title) VALUES (5,3,'Local note')
RETURNING id,published,views;
UPDATE articles SET views=views+2 WHERE id=5 RETURNING views;
DELETE FROM articles WHERE id=5 RETURNING id;
ROLLBACK;

Type these at the psql prompt, not Bash. INSERT supplies three columns; defaults fill false and zero. RETURNING reports the stored row, giving 5 | f | 0. UPDATE calculates from the current stored views, giving 2. DELETE removes only id 5 and reports 5. ROLLBACK undoes the transaction; the temporary setup is still available. Exit psql with \q.

WHERE matters on writes: without it every row is updated/deleted. Preview the same filter using SELECT and check affected rows. UPDATE returning zero rows isn't a SQL error; at the API boundary you may need to interpret it as “not found.” Specifying column names protects an INSERT from depending on physical column order.

Fail on purpose in the temporary sample

In the same sample connection, outside an explicit transaction, attempt INSERT INTO articles (id,author_id,title) VALUES (9,999,'Orphan');. Expect a foreign-key error; there is no author 999. Try a blank title and expect a check violation. Try an existing id and expect a primary-key violation. Each failed standalone statement leaves no new row. Inside BEGIN, the first failure instead leaves the transaction aborted until ROLLBACK; lesson 6 traces that state.

Hint: why checking first is insufficient

Two clients can both SELECT and see no duplicate title before either inserts. A database UNIQUE rule arbitrates when the writes race. The loser must handle the violation and roll back.

Explain the NULL case

An unassigned article is allowed because author_id is nullable. The foreign key checks actual references, not absent ones. Making author_id NOT NULL would change the product rule: every article must have an author.
