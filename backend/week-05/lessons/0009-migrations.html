Week 05 / lesson 09

Change schema with recorded history

Inspect and apply a migration without confusing it with editing a model.

A migration is a versioned program that moves a database schema from one state to another. Models describe the desired shape; migration history describes transitions, including how existing rows survive. Alembic records the current revision in alembic_version. A model file alone cannot tell you which transitions a particular database has applied.

Run an unrelated completed example first

From the weekly root read the supplied demo config, demo runner, and revisions demo1 / demo2. The config points to a script directory; env.py connects only to local w5_demo and runs revisions inside a transaction. demo1 creates labels; demo2 adds a required color with server default gray. These are complete teaching examples, not Task answers.

export DEMO_DATABASE_URL='postgresql+psycopg://postgres:local-only@127.0.0.1:55435/w5_demo'
uv run alembic -c practice/migration-demo/alembic.ini upgrade demo1
psql 'postgresql://postgres:local-only@127.0.0.1:55435/w5_demo' -X -c "INSERT INTO labels(name) VALUES ('before change');"
uv run alembic -c practice/migration-demo/alembic.ini upgrade head
psql 'postgresql://postgres:local-only@127.0.0.1:55435/w5_demo' -X -c 'SELECT name,color FROM labels;'
uv run alembic -c practice/migration-demo/alembic.ini current

Expect before change/gray and demo2 (head) on a first run. If the demo already has rows or is at demo2, inspect current first and record/reuse it rather than forcing a reset. server_default acts in PostgreSQL, including direct SQL inserts. A Python-side default alone would not backfill existing rows. Adding a required column with no value policy can fail when old rows exist.

Inspect rollback before running it

demo2's downgrade drops color: it cannot reconstruct customized color values later. On this disposable demo only, after noting current values, run uv run alembic -c practice/migration-demo/alembic.ini downgrade -1, inspect \d labels in w5_demo, then upgrade head again. The name survives, but a former custom color becomes gray. This is why a schema rollback isn't a data recovery plan. Never blindly downgrade your learner project or shared data; first inspect what will be lost and whether a forward corrective migration is safer.

Your persistent project

Read project alembic.ini, migrations/env.py, script.py.mako and versions/README.md. Leave runner/template infrastructure unchanged. The Mako placeholders fill the generated revision; they are not Python syntax you should paste into models. env.py imports Base.metadata, reads DATABASE_URL and supports online execution or offline SQL generation. It imports models.py, so all mapped classes must be registered there.

source practice/local.env.example
uv run alembic -c projects/task-api/alembic.ini revision --autogenerate -m "create task storage"
uv run alembic -c projects/task-api/alembic.ini upgrade head
uv run alembic -c projects/task-api/alembic.ini current
uv run alembic -c projects/task-api/alembic.ini history
psql "$W5_PSQL_URL" -X -c '\d tasks'

Pause between revision and upgrade: open the new versions/*.py and inspect every operation, constraint name and downgrade. Empty models produce an empty candidate, not a completed deliverable. Autogeneration can mistake renames for drop/add and cannot decide data backfills. Compare the candidate with your design. Don't edit already-applied history to patch later changes; create a new revision.

Hint for safe growth

A nullable new field can preserve old rows; making it required may need adding it nullable, backfilling known values, then setting NOT NULL. The data policy is a design decision, not a generated answer.

Check for schema drift

If the class has a column but psql doesn't, check destination and current revision before debugging the query. create_all does not substitute for migration of existing tables.
