Week 05 / lesson 08

Put the transaction at the boundary

Use a session without committing half an operation.

The Engine holds connection configuration and pooling. A Session coordinates ORM work and a transaction; it is not a global dictionary and must not be shared by concurrent requests. A repository groups queries for a domain operation. Its purpose here is to keep HTTP parsing out of SQL and let one outer boundary commit a complete operation.

Read the complete label example

with Session(engine) as session:
    with session.begin():
        item = Label(name="draft")
        session.add(item)
        session.flush()
        print("flushed", item.id)

with calls a context manager's entry and exit behavior. The outer context closes the session. The inner context begins a transaction, commits on normal exit and rolls back when an exception escapes. Flush sends pending INSERT/UPDATE/DELETE statements and obtains generated values. Another connection must not rely on those uncommitted writes yet. A commit can still fail after flush, so don't return success before transaction exit.

The example's later transaction adds review and duplicate draft. The uniqueness failure causes the whole transaction to roll back, including review. Catch IntegrityError outside the transaction context so rollback has run. Afterwards a fresh SELECT sees draft alone. The example calls rollback after its first SELECT because even a read automatically begins a transaction; calling begin again without ending it raises “a transaction is already begun.”

A query is built, then executed

statement = select(Label).where(Label.name == "draft")
row = session.scalars(statement).one_or_none()

Label.name == "draft" builds a SQL expression rather than comparing two ordinary Python strings. scalars extracts each result's first selected entity/value. one_or_none gives None for no row and raises if multiple rows violate the expected shape. You still need to translate “no row” to your domain's missing-resource behavior. Avoid mixing Python and with SQL expressions; pass conditions to where separately or use SQLAlchemy's operators.

total = session.scalar(select(func.count()).select_from(Label))

row.name = "private"
session.delete(other_row)

These snippets show mechanisms from separate transactions; do not paste them as one unguarded script. func.count builds SQL COUNT; select_from names the table being counted. scalar gives the single count value. The page excludes its first row and returns one name; its size is one while total is three. Assignment to an attached object's mapped attribute marks it changed; the next flush writes UPDATE. session.delete marks a loaded object for DELETE at flush. Neither call commits by itself. Querying with one() raises when no match exists; a user-facing lookup often needs one_or_none() and a deliberate missing branch instead.

Understand the supplied boundary

At the weekly root read db.py, then app.py's repo/transact functions, then repository.py. db.py reads DATABASE_URL and enables a connection health pre-check; it neither migrates nor resets data. repo yields one repository backed by one Session per request. yield hands the dependency to FastAPI, which resumes cleanup afterwards. transact owns begin/commit and converts known domain failures after rollback. Unexpected failures remain failures.

Implement repository.create as a small task-plus-event unit. It may flush to obtain the task ID, but must not commit. The outer boundary commits both rows. Return a plain dictionary while values are available; returning a lazily loaded ORM object after the session closes can cause detached-object errors or unexpected SQL during serialization. A repository-level commit would make the rollback test fail because the task could outlive its rejected event.

Use bound parameters or SQLAlchemy expressions for values; never construct SQL with an f-string containing request input. The quote-like string x' OR true -- must remain a title value, not a condition. Read the parameter check in test_postgres.py; run uv run pytest practice/test_postgres.py -q -k parameter and record what it proves.

Check the failure

If false falls through a truthiness check, the API returns all tasks instead of unfinished tasks. This is a query-construction bug, not a PostgreSQL boolean problem.
