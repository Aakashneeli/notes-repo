Week 05 / lesson 11

Test the failure, not only the happy path

Use a real test database and prove a partial write disappears.

An integration test connects components that can disagree: HTTP validation, repository code, driver and PostgreSQL rules. A mock returning your expected dictionary cannot prove that a foreign key exists or a transaction rolls back. FastAPI's TestClient exercises the application without opening a network port, but these tests still send real SQL to PostgreSQL.

Read the isolation contract first

From the weekly root read tests/conftest.py. pytest discovers fixtures in this filename automatically. The engine fixture refuses targets outside 127.0.0.1:55435/w5_test and refuses custom URL options. It creates a fresh random schema, sets a connection search_path to that schema, and applies your actual Alembic migrations there. After the test it disposes connections and drops only that generated schema. This cleanup deletes test-created data, not your dev tasks. No broad TRUNCATE or shared-database reset is needed.

yield in a fixture separates setup from teardown; pytest injects the yielded engine when a test requests its name. monkeypatch restores environment changes after the test. The Alembic Config points to the project's real config and revisions. An empty migration history produces “EXPECTED STARTER” explicitly. Never hide this by marking the suite skipped: write the migration first. In migrations, keep tables in the active schema rather than hard-coding public, or the isolation is defeated.

Trace an assertion that catches a real bug

Read test_contract.py. Its event-failure test adds a test-only constraint rejecting 'created' events. POST tries to insert a task and then its event. Expected response is 500 for this unexpected test-injected failure; a separate SQL connection must see zero tasks. If the repository committed the task first, that final count becomes one, exposing a partial write. This is stronger than merely asserting “an exception occurred.”

The conflict test creates A and B, attempts to rename A to B and mark it done, then checks A is unchanged and its event count is still one. A following valid create checks recovery. The restart test creates a new app over the same database, catching dictionary substitutes. Direct SQL constraint tests bypass Pydantic, catching models whose rules exist only in the API.

source practice/local.env.example
uv run pytest projects/task-api/tests -q
uv run pytest projects/task-api/tests -q -k event_failure

Run from the weekly root after migrations and your first implementation. A connection failure is infrastructure; missing revisions and NotImplementedError are expected unfinished work; a wrong count/status is a behavior defect. Inspect the first meaningful error before changing several files at once. Tests must not assume generated IDs start at one or are contiguous.

Add your own regression

Edit test_learner.py; this is learner-owned, while supplied contract tests should remain intact. Start with a small variation: PATCH true back to false, then use an independent connection to check the stored boolean and event. Next add competing same-title writes using two separate sessions/connections. Each must commit/rollback independently; assert exactly one succeeds and one gets a uniqueness failure. Give waits a timeout so a test cannot hang forever. Lesson 6 supplies the behavior to predict; deciding the test implementation is your work.

Hint for a regression

Arrange one stored task; act with PATCH false; assert HTTP and SQL values. If you remove the “is not None” filter check, use a list(done=false) test to make the mutation fail visibly.

Check isolation reasoning

A test transaction on one connection cannot automatically roll back commits made on another connection. That is why this suite isolates with a fresh schema and tests real commit behavior rather than assuming a shared rollback fixture cleans everything.

Copy fields from templates/mistake.md into the weekly log for an actual bug. Record failing-before/passing-after and a command someone can rerun. Also test migration on fresh schema and existing rows; passing API CRUD does not prove data evolution. Next, inspect what an index changes—and what it does not.
