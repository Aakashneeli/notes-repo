Week 05 / lesson 06

Make two writes succeed together

Predict commit, rollback and a competing write.

A transaction groups database work into a unit. Suppose creating a task also records a created event. If the task commits first and event insertion then fails, your history lies about stored data. Put both writes inside one transaction; either both commit or neither does. Commit makes the transaction durable under the database's configured guarantees; flush merely sends pending SQL. Neither replaces backups.

Trace the aborted state

At the weekly root open psql "$W5_PSQL_URL" -X and run \i practice/seed.sql. Use this temporary sample:

BEGIN;
UPDATE articles SET views=11 WHERE id=1;
INSERT INTO articles VALUES (5,999,'Bad reference',false,0);
SELECT views FROM articles WHERE id=1;
ROLLBACK;
SELECT views FROM articles WHERE id=1;

UPDATE succeeds inside the transaction. INSERT fails its foreign key. The next SELECT reports an aborted transaction instead of 11. ROLLBACK restores a usable connection and undoes the UPDATE; the last SELECT gives 10. Catching a Python exception alone will not magically repair an aborted database transaction. End it with rollback (or a previously established savepoint, optional later).

Two terminals, one stored value

Temporary tables are connection-local, so use a uniquely named practice table for this concurrency observation. Exit the seed session with \q. In each of two terminals starting at the weekly root, open psql 'postgresql://postgres:local-only@127.0.0.1:55435/w5_test' -X. This deliberately uses w5_test, keeping experimental tables out of the dev schema that Alembic will compare. In terminal A create CREATE TABLE w5_counter_practice (id integer PRIMARY KEY,n integer NOT NULL); then INSERT INTO w5_counter_practice VALUES (1,0);. If it already exists, SELECT it and choose a fresh name for a new attempt; never reset past data. The automated project tests use separate random schemas and do not reset this practice table.

-- Terminal A, connected to w5_test
BEGIN;
UPDATE w5_counter_practice SET n=n+1 WHERE id=1;
-- Leave transaction open.

-- Terminal B, same w5_test in a second psql connection
BEGIN;
SET LOCAL lock_timeout='10s';
UPDATE w5_counter_practice SET n=n+1 WHERE id=1;

B waits on A's row lock. Within ten seconds, type COMMIT in A; then B's UPDATE completes. Type COMMIT in B and SELECT n: expected 2 from initial zero. If B times out, ROLLBACK B, commit A, and retry B's transaction; record the timeout rather than hiding it. Leave the practice table as evidence. Exit both connections with \q.

PostgreSQL's default Read Committed isolation gives statements snapshots; it does not turn a separate read/modify/write sequence into one indivisible action. If both clients read zero then each sends SET n=1, the second may overwrite the first increment. SET n=n+1 computes from the row as updated under the lock. Unique constraints similarly decide competing same-title inserts: one can wait then fail after the winner commits. Sequences may consume IDs on failed transactions, so gaps are normal.

Hint for the explain-back

Separate atomicity (all-or-nothing writes), visibility (what another transaction sees), and conflicts (which writer waits or fails). “Transactions prevent all races” is too broad.

Check your reasoning

After A rolls back instead of committing, B increments the original zero and the final value is 1. A successful increment is not lost; A's work was intentionally undone.

Independent variation: repeat with a new row ID and A rolling back. Record actual behavior, then explain how the same-title race should appear as a conflict to an API client.
