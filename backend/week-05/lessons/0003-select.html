Week 05 / lesson 03

Predict a filtered page

Write a SELECT whose rows and order you can predict.

A table has named columns and rows. A SQL query describes which rows you want; PostgreSQL chooses how to fetch them. For reasoning, read a simple query as source rows → filter → choose columns → order → take a page. This reasoning order is not a promise about its physical execution plan.

From the weekly root read practice/seed.sql, the supplied sample authors/articles. Asha has articles 1 and 2; Ben has 3; Chen has none; article 4 has no author. published is true for 1 and 3. Seed uses TEMP tables: they exist only in that connection, so project tables are untouched. Read worked.sql and run:

psql "$W5_PSQL_URL" -X -f practice/worked.sql

-f executes a file; \ir seed.sql loads a file relative to that script. ON_ERROR_STOP stops scripts on SQL errors. Without it, a later success can hide an earlier failure. The first output is 1 | SQL notes. The later outputs are explained in lessons 5 and 6; don't count this supplied query as your own.

SELECT id,title FROM articles
WHERE published = true
ORDER BY id
LIMIT 1;

Rows 1 and 3 pass the filter; only id/title are returned; ordering puts 1 first; limit retains it. Removing ORDER BY means SQL doesn't promise which qualifying row comes first. OFFSET 1 LIMIT 1 after that order would return article 3. Page counts must count the filtered set before applying the limit.

Missing is not false

NULL represents absent/unknown data, not zero, false or empty text. author_id = NULL doesn't evaluate true even on an unassigned row. Use author_id IS NULL. A filter retains only true expressions; false and unknown are discarded. SQL strings use single quotes: title = 'Draft'. Double quotes identify names, so "Draft" means a column named Draft.
