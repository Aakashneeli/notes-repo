Return acceptance before processing

Use BackgroundTasks while explaining its lifetime and limits.

Read demo_app in practice/examples.py. The handler appends “handler,” registers a function with add_task, and returns an accepted response. The registered function appends “after-response.” Passing the function object schedules it; calling it first, as in add_task(record("done")), executes immediately and passes its return value by mistake.

tasks.add_task(record, "after-response")
# record: callable, no parentheses here
# "after-response": argument stored for its later call
# Response body is prepared before that call.

On the wire, a client can receive 202 before processing finishes. It must poll GET /jobs/{id}; 202 does not promise success. A synchronous task runs through the framework's thread-pool support, while an async task must cooperate with the event loop. Calling blocking I/O or heavy CPU work inside async def does not become nonblocking by spelling it async. Keep this lab's extraction tiny.

BackgroundTasks lives in the API process; there is no durable external queue. Restarting or crashing the process can lose scheduled work even though SQLite still says pending. A catch block cannot run after process death. Pass persistent identifiers and long-lived adapters, not request-scoped UploadFile or database connections. Log one safe event

In your worker module, logging.getLogger(__name__) names the logger after the package/module (for example ingestion.worker). logger.info("job_state job_id=%s state=%s", job_id, "running") records only selected fields; %s placeholders are filled by logging. It must not include upload bytes, the API key or a raw exception string. The test’s caplog fixture temporarily captures those INFO records; Uvicorn's normal console configuration may filter them differently. A test proves only the events it exercises. For syntax help, use the small logging bridge.

Do not misread TestClient

TestClient waits for response background tasks before returning control to your test. Its immediate GET may already see completed. This is useful for deterministic unit checks but does not measure real HTTP response timing or process-crash durability. The acceptance body should still say pending, because it describes acceptance at response construction.
