Keep metadata durable and queries parameterized

Trace the supplied repository and its atomic claim.

Read repository.py slowly. Its one jobs table is a minimal fixture joining document metadata and job fields for one ingestion attempt. The primary key is the job ID; storage_key is unique; size is positive; state has an allowlist constraint. It is not the final schema for multiple users, document versions or several jobs per document. Explain these limits in design.md before relying on it.

db.execute("SELECT * FROM jobs WHERE id = ?", (job_id,))
# SQL structure is fixed. The tuple supplies one value.
# The trailing comma makes (job_id,) a tuple, not a grouped expression.

For job ID j1, the driver binds that value to the placeholder. For ' OR 1=1 --, it still binds one value; it does not broaden the query. An f-string that inserts that text into SQL would change the query grammar. ORM use is not protection if you concatenate user text inside raw SQL. Identifiers such as column names require server-side allowlists, not value placeholders.

with closing(self.connect()) as db, db: combines two context managers: the connection transaction commits on success or rolls back on exception; closing then releases it. Each call owns a fresh connection, safe to use from the thread executing that call. It does not keep a request's connection alive for later work. sqlite3.Row permits named fields, and converting to dict keeps returned data usable after closing.

UPDATE jobs SET state='running', attempts=attempts+1
WHERE id=? AND state='pending'
# actual fixture binds target and expected too
# caller A changes one row -> True
# caller B finds no pending row -> False

This compare-and-set prevents two cooperating workers from claiming the same pending row. A separate get followed by an unconditional update leaves a race: both workers can read pending first. The SQL constraint only restricts the set of names, not allowed arrows; worker/service policy must enforce transitions. A process crash can strand running forever without a lease or explicit recovery policy.

For the security boundary, compare this binding example with OWASP parameterized-query guidance.

First hint

The second caller compares against the current stored state, not its old Python copy.

Explained beginner answer

Only the first matching UPDATE increments attempts. A transaction commits the whole statement atomically. Two successful HTTP uploads still create two jobs: claim idempotence is different from upload deduplication.
