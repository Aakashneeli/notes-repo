Week 06 / Lesson 08

Make failure visible

Define valid state changes and a bounded retry policy.

A status is a durable answer to “what happened to accepted work?” Pending means accepted but unclaimed. Running means claimed, not necessarily still alive. Completed means result metadata is committed. Failed means this attempt ended without a usable result. Retrying means a transient failure has been classified for another attempt. A queue's internal status and your domain status can disagree; expose your own documented contract.

pending -> running -> completed
                 \-> failed
                 \-> retrying -> pending -> running
# Base BackgroundTasks project uses the first two terminal paths.
# The retrying path is modeled now and specified in the required RQ note.

Trace a missing file: pending row exists; claim changes it to running and increments attempts; storage.read raises FileNotFoundError; worker commits failed with error_code=storage_missing. A stable code helps clients without exposing an absolute server path. If the metadata database itself is unavailable, even failure recording can fail: retain a safe server log and reconcile later. Never return a fake completed state to hide that uncertainty.

A transient error may disappear on a later attempt (temporary busy storage). Invalid content will not improve by repeating it. Retry only classified transient failures, cap total attempts and delay repeats. For max_attempts=3, failure at attempt 1 may retry; failure at attempt 3 must fail. Retrying forever can multiply load during an outage.

First hint

Both the error classification and remaining attempts must permit retry.

Explained beginner answer

Return "retry" if error_code == "storage_busy" and attempts < max_attempts, else "fail". This decision alone schedules nothing; a dispatcher must implement it and persist the transition.

Independent variation

A worker writes output and crashes before marking completed. Would retry append the text twice? Define idempotence: repeating a job has the same intended effect as one successful execution. Prefer replacing deterministic results for a job ID, not appending duplicate records. Document why completed-job no-op and a claim protect this local project, yet abandoned running still needs recovery.
