Separate client names from storage keys

Store under server-controlled paths and explain partial failures.

An original filename is metadata, not a filesystem instruction. Joining a storage root with ../../notes.txt may escape the directory. Even using just the basename risks collisions and overwriting. Generate a UUID hex key, append .txt, validate that internal key on every storage operation, and keep originals out of returned paths and logs. The contract uses exactly 32 lowercase hexadecimal characters plus .txt.

from uuid import uuid4
key = uuid4().hex + ".txt"
# Example shape, not a fixed output: 32 lowercase hex characters + .txt
# root / key now has no client-selected path components
with (root / key).open("xb") as stream:
    stream.write(data)

Path / name constructs a path. The x in xb means exclusive creation: an existing object raises FileExistsError rather than being overwritten. The b means write bytes. Create only the configured private root with parents=True and exist_ok=True. A trusted local directory is a prerequisite; these checks alone do not defend a root an attacker can replace with symlinks. For this tiny lab the validated bytes are bounded in memory. Larger uploads need a more elaborate temporary-file and publication protocol.

Ordering is a consistency decision. Save the blob first, then create metadata. If metadata creation raises, remove only the blob created for this attempt and propagate the failure. If a process dies between operations, Python cleanup cannot run: an orphan blob may remain. If metadata is committed but scheduling is lost, a pending row may remain. A reconciliation policy inspects old rows/blobs and handles them deliberately; never silently delete all runtime files as a fix.

First hint

Validate the whole internal key before any read, write or deletion. Cleanup after write failure must not remove a preexisting file.

Explained beginner answer

Use a full-match check for [0-9a-f]{32} followed by .txt. Acquire exclusive creation before entering a cleanup block. If creation itself raises FileExistsError, there is no newly owned file to delete.

Local to S3, a note rather than provisioning

S3 identifies an object by bucket and key; a key is not a local directory path. Keep stable storage keys in metadata and replace put/read/delete behind the adapter. Document private access, credential delivery, read/write failures, metadata commit ordering and cleanup. Live S3 requires an AWS account, permissions and request/storage/transfer costs; do not create anything for this exercise.
