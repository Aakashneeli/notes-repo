Week 06 / Lesson 10

Move scheduling across a process boundary

Explain Redis/RQ and write a concrete migration note; optionally run a local queue.

Redis is a server storing data structures by key. Strings can cache values or count events, lists can model queue-like data, and hashes can hold fields. A cache may expire; it is not automatically your durable job truth. A rate-limit counter needs atomic increment/expiry behavior and a defined window. Do not reuse a disposable cache policy for critical queued work.

RQ uses Redis to hold queued job information. Your producer enqueues an importable function and arguments. A separate worker consumes the named queue and runs the function with compatible code and access to inputs. It cannot share the API's Python objects. Send job_id and reconstruct storage/repository from worker settings. Redis accessibility, persistence/eviction policy and worker supervision matter; introducing a queue does not guarantee exactly-once effects.

producer -> Redis queue "week6" -> worker -> count_words(text)
                                      <- result: 4
# rq_task.count_words is importable by both processes
# text is serialized; do not send file handles, requests or credentials

Write projects/ingestion/rq-migration.md even if you skip the optional lab. Specify dispatch after metadata commit, a stable job identifier, worker inputs, retry classification, recovery for stale running, and reconciliation for commit-success/enqueue-failure. RQ's scheduled retries need a scheduler-enabled worker when intervals are used. Map queue states to the five domain states deliberately; no automatic alias is guaranteed.

Primary details: Redis structures, RQ retries and worker CLI and serializer trust.

Optional local queue lab

Only if an isolated Redis server and redis-cli are already installed: use a dedicated port 6386. No managed account or paid service is needed. Read practice/rq_task.py and practice/rq_enqueue.py as completed queue-only examples. They do not implement your ingestion worker. From the weekly root run:

uv sync --locked --extra rq
mkdir -p runtime/redis
redis-server --bind 127.0.0.1 --port 6386 --dir "$PWD/runtime/redis" --appendonly yes

Leave that terminal open. If the port is occupied, stop and choose a dedicated alternative in all commands; never flush an existing server. In a second terminal, start at the weekly root, then change explicitly into practice so both producer and worker can import rq_task:

cd /home/an10/code/notes-repo/backend/week-06/practice
uv run --extra rq rq worker --url redis://127.0.0.1:6386/0 --with-scheduler week6

In a third terminal start in the same practice directory and run uv run --extra rq python rq_enqueue.py. Copy its returned ID. To fetch later, run the following there, replacing JOB_ID:

uv run --extra rq python -c 'from redis import Redis; from rq.job import Job; j=Job.fetch("JOB_ID", connection=Redis.from_url("redis://127.0.0.1:6386/0")); print(j.get_status(), j.return_value())'

Expected: finished status and result 4 after execution. Initially queued/started is legitimate. Stop only the worker and server you started with Ctrl-C, preserving runtime/redis if you want to inspect persistence. Return to the weekly root with cd ... Log commands, IDs and observations in weekly-logs/week-06.md; if tools are missing, label live RQ unperformed and finish the migration note.

RQ defaults to pickle serialization, which requires a trusted, access-restricted Redis instance. Do not connect this example to an untrusted queue. Production workers should also disable job-description logging and avoid sensitive arguments; the teaching phrase here is public. Queue results expire, so query promptly; the durable domain result must live in your metadata store.

Failure and independent variation

Stop the worker, enqueue once, then restart it: work should wait in Redis. Contrast this with the API-process queue. A failing RQ function must propagate its error for RQ retry machinery to act; merely swallowing an exception and returning a failed dictionary looks like successful function execution to RQ. Explain that distinction in your migration note.

Primary reading: python-rq.org — relevant official guide. See annotated sources for supporting API and security documentation.
