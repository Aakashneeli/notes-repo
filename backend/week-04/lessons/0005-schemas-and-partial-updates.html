Validate creation and partial updates

Two passes: first understand and predict; then run the guided check. Pause between sections when needed. Worked mechanism and debugging practice.

Separate omitted values, nulls and false values.

A schema is an explicit description of allowed data. Creation input does not include a server-generated ID. A read response includes it. A partial update includes only fields the client supplied. Using one model for all three confuses required input with stored output and can expose internal fields. In this project you will author schemas.py; its docstring states the contract, not an implementation.

The completed GreetingIn uses ConfigDict(extra="forbid", str_strip_whitespace=True) and a constrained name field. Trace {"name":" Ada "}: JSON object → model construction → whitespace trimming → length check → payload.name is Ada. A blank name fails after trimming. Extra fields are rejected instead of silently ignored. Request validation failure is a client error; a broken response model points to an application bug and belongs to server-side diagnosis.

In our Task contract, title must be a string trimmed to 1–80 characters, and done must be a strict boolean. The query done=true must parse text, but JSON "done":"true" is a string and is deliberately rejected. This distinction is a teaching contract, not an HTTP rule. Pydantic's normal coercion and strict field validation are different choices.

Omitted is not null

from pydantic import BaseModel

class CupPatch(BaseModel):
    hot: bool | None = None

print(CupPatch().model_dump(exclude_unset=True))
print(CupPatch(hot=False).model_dump(exclude_unset=True))
print(CupPatch(hot=None).model_dump(exclude_unset=True))

The outputs are {}, {'hot': False} and {'hot': None}. exclude_unset=True filters on what was supplied, not on truthiness or equality to defaults. This permissive teaching model allows None; your TaskUpdate must additionally reject explicitly supplied null. A before-model validator can inspect key presence and reject None before field conversion. Then validate the merged candidate before mutating memory. Do not use model_copy(update=...) as if it validates arbitrary new values.

class DialInput(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)
    label: str = Field(min_length=1, max_length=12)
    level: int = Field(strict=True, ge=0, le=5)

Step 1: BaseModel provides construction and validation behavior; your subclass declares the allowed fields. Step 2: calling DialInput(label=" desk ", level=0) supplies keyword arguments. Step 3: configuration strips the label's surrounding whitespace and rejects undeclared keys. Step 4: the label length and level's type/range must pass. Step 5: the constructed instance holds label desk and level 0; model_dump makes a normal dictionary suitable for further processing. ge means greater than or equal to, and le means less than or equal to.

Zero is valid because the range includes it. The string "2" is invalid here even though a person could interpret it as two: strict validation deliberately refuses that conversion. True is also rejected as a strict integer input, although Python considers bool a subclass of int. A label containing only spaces becomes empty before the minimum-length check and fails. These details should be decisions you understand, not magic inherited from a copied model.

Read a validation failure

Pydantic raises ValidationError when constructing a model directly with bad data. Its errors() result is a list of structured problems. A location such as ('level',) names the affected field; type classifies the problem; msg describes it. Parentheses with a trailing comma represent a one-item tuple in Python. This is useful inside a controlled local test. The project's public error handler should still return the small sanitized envelope, not all the raw details.

First hint

Separate whether a field was sent from whether its value is allowed.

Reasoned answer

For a done-only update, title was not sent and must be preserved. If done was sent as null, it was sent but is invalid under our contract. If done was sent as false, it is both sent and valid. Therefore neither “drop every false-like value” nor “allow None because the field is optional” expresses the required policy.

Keep request validation and service rules separate: a title can satisfy every string constraint yet still conflict with an existing task. A model validates this input's shape; the service compares it with current state. That is why 422 and 409 can arise at different points.
