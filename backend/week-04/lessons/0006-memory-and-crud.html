Build the in-memory behavior

Two passes: first understand and predict; then run the guided check. Pause between sections when needed. Worked mechanism and debugging practice.

Separate state changes from HTTP choices.

CRUD means create, read, update and delete. The service owns those rules; a router translates between HTTP and the service. A task store may use an ordinary dictionary keyed by ID and a next-ID counter. That is task data, not an algorithm interview exercise. Your choices of functions/classes and signatures belong to you; the black-box tests require public API behavior, not an exact internal arrangement.

Edit service.py. Each service instance starts empty. First creation receives ID 1; deletion does not rewind the counter. Titles are unique after trimming, case-sensitive. A repeated title conflicts even if a client repeats POST because it missed a response. When renaming a task, exclude that same task from the duplicate check. Returning mutable internal objects can let callers change storage accidentally: return copies or validated output records and explain your choice.

Trace a state transition on paper

Start with empty memory and next ID 1. Create title A: store {1: A}, next ID 2. Create B: add ID 2, next ID 3. Delete 1: store only B, next ID still 3. Create C: ID 3. Get 1: missing-resource domain error, no mutation. A normal service result contains data; a domain error describes a business failure without knowing whether a caller is HTTP or a terminal program.

For PATCH, obtain the old task, construct a candidate with supplied changes, validate candidate, check duplicate constraints, then replace stored state. Mutating done before checking a duplicate title leaves a partial write after a rejected request. This is observable with the conflict test. Empty PATCH is the deliberate project policy 400 empty_update; duplicate title is 409 conflict. Those policies are supplied course contracts, not universal requirements for every Task API.

In-memory data lasts only in this app process. Restart loses it. Two worker processes would hold different stores. Plain def handlers may run on different threads; a compound duplicate-check/increment/store can interleave. For this local lab, use a lock around those compound operations and explain that a thread lock does not coordinate separate processes. Keep one worker. Durable storage is next week's topic and is not implemented here.

A complete service small enough to trace

Read Counter and LimitReached in practice/mechanisms.py. This completed counter has one state change, not task CRUD. It demonstrates why a class can be useful: each instance carries its own current value and maximum between calls. self names the instance receiving the call. An underscore signals an internal attribute by convention; it does not encrypt or enforce privacy.

counter = Counter(maximum=2)
print(counter.advance())  # 1
print(counter.advance())  # 2
# A third advance raises LimitReached; stored value stays 2.

Trace the third call: self._value is 2; candidate becomes 3; 3 exceeds the maximum; raise exits the method immediately; the assignment to self._value is never reached. A caller can catch LimitReached and choose a useful response. The service does not decide that the response is HTTP 409 because it should also make sense to a non-HTTP caller.

Now imagine the wrong order: increment self._value first, then check the maximum. The third call would report failure while retaining 3. Even if the router returns the right error code, the state is wrong. This is the same category of bug as updating done before noticing a conflicting title. Put the check before the durable effect, and test the state after the failure.

Observe ownership of state

snapshot returns a new dictionary containing the current number. Editing that returned dictionary cannot change the counter's internal integer. It is not a universal deep-copy solution: if a returned object contains nested mutable lists, copying only its outer dictionary can still share those lists. Our task fields are scalar values, which keeps the present ownership problem smaller.

Why not just a dictionary at module scope?

A module-level dictionary survives between calls, but any user of that module sees the same object. Two app factories and two tests could share it accidentally. Creating a service per app gives ownership a visible place. The router asks for the app's service; the service owns memory; tests create a new app when they require a clean start. “Class” is not automatically clean design—the useful property here is explicit ownership.

First hint

Ask which line can still run after raise, and who owns the object being edited.

Reasoned answer

No later line in that execution of advance runs after raise. Catching the error at the caller does not rewind a mutation already made. That is why checking a response status alone cannot prove rejected operations preserved state.
