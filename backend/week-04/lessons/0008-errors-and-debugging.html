Choose errors and preserve the contract

Two passes: first understand and predict; then run the guided check. Pause between sections when needed. Worked mechanism and debugging practice.

Turn failures into consistent, meaningful responses.

A status code explains the category of outcome; the JSON error explains this API's specific failure. All project errors use {"error":{"code":"not_found","message":"Task not found"}} with nonempty strings. The exact human message can vary. Error codes are stable for clients. Never wrap a failed request in status 200 merely because JSON was returned.

StatusMeaning herecode

400 vs 422 is a documented API design choice here: FastAPI request validation defaults to 422; our empty valid update has a separate business policy. 401 asks for usable authentication; 403 says authenticated identity lacks permission. Do not “fix” an internal KeyError by relabeling everything 400. The framework also returns 405 for an unsupported method; preserve its Allow header and use method_not_allowed.

Edit errors.py. A domain exception should be converted at the HTTP boundary. Register a handler for Starlette's HTTPException so framework-generated 404/405 join route-raised errors. FastAPI's RequestValidationError is separate; unexpected Exception needs a generic 500 handler. Preserve supplied HTTP headers when building a JSONResponse. Do not serialize full validation errors indiscriminately: input/context can contain sensitive or non-JSON values.

A miniature worked handler

Read invalid_request in practice/hello_api.py. The decorator registers the exception type. Its async function receives the request and exception; it returns JSONResponse(status_code=422, content=...). This example deliberately sanitizes the public body. It does not unify every error; compare the 404 you observed in lesson 4. The project must complete that work.

Four different failures that can look alike

Model failure: constructing a model directly raises Pydantic ValidationError. Request failure: FastAPI cannot produce valid request arguments and uses RequestValidationError. Domain failure: your ordinary service raises a meaningful business exception, like the counter's LimitReached. Programming failure: a wrong key access or invalid output reveals a bug. Collapsing all four into one broad except block prevents you from finding the actual cause.

An exception handler is an adapter: it receives an exception and produces an HTTP response. That handler must set both status and content. Returning {"error": ...} from an ordinary successful route without changing status can produce a misleading 200. Conversely, raising an HTTPException interrupts normal route flow. The word “raise” means transfer control through exception handling; it does not mean “return this JSON value.”

Follow a negative test to its conclusion

Take GET /tasks/nope with a valid key. The route path pattern can match, but nope cannot become the required positive integer. Expected: 422 validation_error; the service should not look for a task whose ID is the string nope. Compare GET /tasks/999: conversion to 999 succeeds; the service then discovers no task and returns a domain failure translated to 404. One input has the wrong form; the other has a valid form but no corresponding resource.

Take a valid PATCH that proposes a duplicate title and done=true. Both fields can validate. The duplicate rule then rejects the change with 409. Follow it with a GET and check done is unchanged. Without that follow-up assertion, a half-applied update could escape your test suite.

First hint

Distinguish the Python testing process from the HTTP client response.

Reasoned answer

By default, the Python test can receive the original RuntimeError directly. With raise_server_exceptions=False, it can inspect the generated 500 response. Neither mode fixes the RuntimeError; they answer different diagnostic questions. The public 500 check must additionally assert a generic body without private details.

Debugging ladder: confirm the URL/method; inspect status and body; verify input sources; see whether the handler ran; narrow service state; read the server traceback for 500. With TestClient the default re-raises server exceptions. raise_server_exceptions=False lets you inspect the HTTP 500 response; it does not repair the underlying bug.
