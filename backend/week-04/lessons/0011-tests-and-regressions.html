Week 04 / lesson 11

Prove behavior, then expose a bug

Two passes: first understand and predict; then run the guided check. Pause between sections when needed. Worked mechanism and debugging practice.

Use isolated API checks and write a meaningful regression.

An API test sends an HTTP-shaped request to the app and inspects its response. TestClient runs the application in-process; it exercises routes, validation, dependencies, service logic and serialization without a listening port. It does not prove DNS, TLS, proxy behavior or Postman configuration. A unit test isolates a smaller function/service. Both can be useful; this week requires API tests for every endpoint and negative case.

Read tests/test_contract.py. The client fixture uses monkeypatch to supply dummy environment keys, creates a fresh app, opens a TestClient context and yields it to each test. Teardown exits lifespan and restores environment values. This prevents order-dependent leaked state. Parametrize repeats one behavior for several inputs; each is a separate test. Helpers create and error centralize setup/envelope checks; read them before diagnosing assertion output.

Trace test_crud_and_id_policy: create trimmed title → assert 201 and exact fields → GET with read key → PATCH done → PATCH only title preserves done → DELETE gives empty 204 → later GET/DELETE give 404 → next creation receives ID 2. Exact content checks catch more than a status-only assertion. test_list_filter_before_slice uses a deliberately interleaved fixture to expose the common slicing-order bug. test_unexpected_error_is_generic adds a route only to the test app to trigger a server failure.

Read assertions as claims, not ceremony

Consider assert response.status_code == 201. Python evaluates the comparison; if false, pytest reports a failure with the actual values. The next assertion can check the returned title and ID. A test that only checks “response exists” proves very little, since an error response also exists. Write down the incorrect implementation each assertion would catch.

Read test_counter_state in practice/test_mechanisms.py for a complete, short test. Arrange: create a fresh Counter. Act/assert: two calls return 1 and 2. Expect failure: the third call must raise LimitReached. Inspect afterward: snapshot must still be 2. This last line is essential. It exposes a service that increments first and then complains.

with pytest.raises(LimitReached):
    counter.advance()
assert counter.snapshot() == {"value": 2}

The with block succeeds as a test only when the expected exception is raised. If the call unexpectedly succeeds, pytest reports “DID NOT RAISE.” An unrelated exception also fails the test. This is why a negative test can pass while the operation itself correctly fails. Do not remove the expected exception just to make every operation look successful.

Read a fixture in execution order

For each test requesting client, pytest calls the fixture. monkeypatch sets the dummy keys; create_app constructs fresh state; entering TestClient runs lifespan; yield hands the client to the test; the test sends requests and evaluates assertions; control returns to the fixture; the context exits; monkeypatch restores the prior environment. The fixture's name is how pytest supplies its value as the test argument. It is not a globally shared variable you must import.

Parametrize expands cases before execution. The ten missing/wrong-auth cases are two header choices multiplied by five operations. A failure on POST does not prove DELETE is protected. Keeping those cases separate makes a missing dependency on one route visible.

First hint

A correct 403 is only half the claim. Check the effect the rejected request must not have.

Reasoned answer

Assert both the denial and the subsequent unchanged record. A buggy handler could mutate state before checking permission and still return 403. The second request makes that hidden side effect observable through the public API.

Debug deliberately

On your own uncommitted implementation, save the current state, temporarily invert one filter or drop the permission check, and predict which specific tests should fail. Run them, restore the code you saved, rerun. Never use git reset --hard or checkout to discard unrelated work. A check that still passes a meaningful wrong implementation is a test gap. Author verification of these materials checks selected mutations separately; it does not mark your work complete.
