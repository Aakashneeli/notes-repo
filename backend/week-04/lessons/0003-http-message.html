Read the HTTP message

Two passes: first understand and predict; then run the guided check. Pause between sections when needed. Worked mechanism and debugging practice.

Identify method, target, headers and body before writing a route.

HTTP is a client/server message protocol. The client sends a request; the server returns a status, headers and usually a body. A resource is the thing an API names, such as one task. A representation is data describing that thing, such as JSON. A route combines a method and path pattern to select behavior.

POST /greetings HTTP/1.1
Host: 127.0.0.1:8004
Content-Type: application/json
X-Badge: practice

{"name":"Ada"}

Trace this message: POST asks the greeting route to process a body; the path is /greetings; Host selects the server authority; Content-Type describes the bytes sent; X-Badge carries practice credentials; the blank line separates headers from the JSON body. JSON uses double-quoted keys and lowercase true/false/null; Python uses True/False/None. Headers are metadata, not fields automatically included in your Pydantic body model.

GET reads a representation; POST commonly creates under a collection; PATCH applies a partial change; PUT conventionally replaces the target representation; DELETE removes it. This course chooses PATCH for updates and does not require PUT. GET should not create a task. Repeating a DELETE can return a different status while leaving the same final state—idempotency concerns intended server effects, not byte-identical responses. POST creation is not assumed safe to retry automatically.

A 2xx response means success, 4xx says the request cannot be fulfilled as sent, and 5xx identifies a server-side failure. A 201 response marks creation; 204 has no response body. Client code that blindly calls JSON decoding after a 204 will fail. Content-Type describes the actual representation; Accept expresses what the client prefers. This week's API documents JSON and does not implement full content negotiation.

Worked trace: what crosses the boundary?

Suppose Python holds {"name": "Ada"}. That dictionary is not transmitted as a Python object. Your client encodes it into JSON text, then bytes. The server receives those bytes and decodes them. Only then can it construct a model. This distinction explains why a traceback can say “JSON decode error” before it mentions any field: malformed syntax prevents model validation from even receiving an object.

Compare three failures with the practice badge present: body { cannot be parsed; body {"name": 7} parses but fails the name contract; body {"name": "Ada"} parses and validates. The first two produce 422 in the example, but for different reasons. A status alone does not identify the failing layer. Our sanitized error response intentionally hides details; use the controlled test input to reproduce and investigate, rather than returning private request contents to a client.

When curl shows headers followed by JSON, distinguish response headers from your request headers. -i shows response headers. Use -v for a local diagnostic transcript if needed: lines starting with > are sent and lines starting with < are received. That transcript can contain credentials, so use only this lesson’s public practice badge and do not paste private headers into evidence.
