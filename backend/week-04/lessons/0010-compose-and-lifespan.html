Week 04 / lesson 10

Compose the app and understand its lifetime

Two passes: first understand and predict; then run the guided check. Pause between sections when needed. Worked mechanism and debugging practice.

Connect modules without sharing state between tests.

In a composition root, dependencies are created and connected in one place. Here that is create_app() in main.py. Construct one TaskService per app, attach it to app.state, register handlers and include the task router. Routers depend on schemas and service access; the service depends on ordinary Python/domain rules, never main.py. Importing main from the service creates an unhelpful cycle.

Function vs class is a practical choice. A pure transformation needs no instance; a service maintaining task memory and a lock has a reason to be instantiated. Keep HTTP response/status details in the adapter. Do not introduce a database repository layer with no purpose simply to match a diagram; this week requires clear router/schema/service separation.

Process lifetime differs from request lifetime

The greeting example's @asynccontextmanager function sets ready before yield, serves while suspended, and clears ready during shutdown after yield. This is FastAPI's lifespan interface. It can later manage resources that need setup/cleanup; the in-memory task app does not need fake database connections. Prefer lifespan for such work rather than mixing old startup/shutdown event handlers with it. Shutdown is not guaranteed after a forced process kill, and it does not make memory durable.

The example tests use with TestClient(app) to execute lifespan entry/exit. Plain TestClient construction does not itself prove startup behavior. Async means cooperative waiting at await points; it does not make a CPU-bound task or blocking call automatically concurrent. Our short memory handlers can use normal def. If you need a refresher, return to the existing async bridge only as needed.

Build one vertical slice and watch the boundary

A vertical slice is one small behavior connected all the way from request to response. Once your schema and service exist, wire only creation and reading one task first. In main.py construct the service, register handlers and include the router. In routes.py delegate to that service. Send a valid creation request, inspect its ID, then GET that ID. After that works, add list/update/delete. This is an implementation order; the final contract still requires all five operations.

Keep a module trace next to the HTTP trace: Uvicorn calls main.create_app once to create an app; main assembles objects and routes; a request resolves dependencies and schema input; the chosen route calls the service; the returned record is checked against the response schema. Calling create_app for every request would keep discarding memory. Creating a global service once for every app would instead share state too broadly. The desired ownership boundary is one service per app instance.

What does with actually buy the test?

A context manager has entry and exit behavior surrounding a block. In with TestClient(app) as client:, entry runs the app's lifespan startup, the block sends requests, and exit runs shutdown. In the greeting lifespan, code before yield is startup and code after yield is shutdown. yield marks the point at which the context manager lets its caller do the work inside the block; it is not a response from your endpoint.
