Week 04 / lesson 12

Use curl, Swagger and Postman together

Two passes: first understand and predict; then run the guided check. Pause between sections when needed. Worked mechanism and debugging practice.

Prepare and export reproducible manual checks.

Automated tests are repeatable code checks. Manual tools let you inspect a running process, tweak input and diagnose what an actual HTTP client sees. OpenAPI is a machine-readable API description at /openapi.json; Swagger UI at /docs turns it into an interactive form. Generated docs describe declared schemas; they do not prove your business rules work. Swagger's default assets may need internet even when the API itself is local.

Read the three supplied sample bodies in data/create.json, data/update.json and data/invalid.json. They are fixtures: valid creation, done-only update and invalid types/whitespace. Leave them unchanged so example commands remain reproducible; use separate new files for variants.

Try it · from the weekly root

Start in /home/an10/code/notes-repo/backend/week-04. With the project server running from lesson 10, send file bytes with curl from this weekly directory. On a fresh server the first ID is 1; otherwise substitute the returned ID in later commands.

curl -i http://127.0.0.1:8004/health
curl -i -X POST http://127.0.0.1:8004/tasks -H "X-API-Key: local-study-key" -H "Content-Type: application/json" --data-binary @projects/task-api/data/create.json
curl -i "http://127.0.0.1:8004/tasks?done=false&offset=0&limit=2" -H "X-API-Key: local-read-key"
curl -i -X PATCH http://127.0.0.1:8004/tasks/1 -H "X-API-Key: local-study-key" -H "Content-Type: application/json" --data-binary @projects/task-api/data/update.json
curl -i -X DELETE http://127.0.0.1:8004/tasks/1 -H "X-API-Key: local-study-key"

Check: Health 200; create 201; list 200 with filtered total; update 200 with done true; delete 204 and no body. A repeated creation title may correctly return 409.

Postman is a learner action

Use a local Postman installation that can reach localhost; the web client may require its desktop agent. Download/install/login steps depend on your environment. No account changes, cloud sync or messages have been performed for you. Do not upload real keys. Local Python/curl practice has no paid service requirement; if a Postman account or feature asks for payment, stop that workflow and record the limitation rather than buying access.

Import postman/task-api.starter.postman_collection.json and local.postman_environment.json. These are supplied starter infrastructure, not evidence of your exported collection. Select the local environment. Its base_url and public dummy keys let the same requests run locally; task_id is filled by the creation response script. Never assume variable edits in one scope affect another.

Restart your disposable in-memory server for a clean sequence. Run the ordered collection: create, list, get, update, invalid payload, missing auth, wrong auth, read-only write, missing resource, delete, get deleted. Inspect Tests results, not just a green send indicator. Each post-response script calls pm.test and compares an observed value; the create script saves task_id only after 201. The starter title is fixed, so rerunning create before deletion can produce an intentional conflict. Inspect the request's resolved URL/header when a variable appears not to work.

Add your own duplicate-title and pagination assertions, including response-body checks. Export the modified collection via its menu's Export action as Collection v2.1 into projects/task-api/postman/task-api.postman_collection.json; this is a future learner-created deliverable. Export no private environment values. Re-import your export and rerun from a clean server. Save the run date, app state, failed/passed checks and export path in the weekly log. Merely parsing JSON does not prove Postman executed it.

Trace one Postman script before running a collection

In the supplied collection, the create request has a post-response script. pm.response.code is the received status; pm.response.json() parses the response body; pm.environment.set("task_id", ...) stores the created ID in the active environment. Later URLs containing {{task_id}} are resolved from that variable. This ties the workflow to an observed server-generated ID, not a guessed constant.

The script stores an ID only after 201. If creation fails with 409 and an older ID remains in the environment, blindly running the remaining requests can test the wrong task. Stop at the first unexpected result, inspect the create response, and restart with a clean disposable server or a clearly chosen task. Record the state you used. A collection is a sequence of stateful interactions, not just eleven unrelated buttons.

pm.test("Created title", () => ...) registers an assertion with a readable label. pm.expect(actual).to.eql(expected) compares values; include an assertion about returned data, not only status. For DELETE, use response.text() to check the empty body rather than parsing nonexistent JSON. For an invalid request, assert the expected error code rather than assuming every 4xx is acceptable.
