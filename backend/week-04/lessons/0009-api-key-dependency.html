Protect every task operation

Two passes: first understand and predict; then run the guided check. Pause between sections when needed. Worked mechanism and debugging practice.

Reuse authentication and distinguish permission checks.

A dependency is a callable FastAPI runs to supply a value or enforce a precondition. Depends(require_badge) passes the function object for later execution; Depends(require_badge()) would call it too early. The greeting example reads a header and raises HTTPException before the route performs useful work. A dependency graph may involve both validation and dependency work; do not assume one universal error priority when several parts of a request are invalid. Our tests isolate one defect at a time.

The assessed API uses X-API-Key. APIKeyHeader(name="X-API-Key", auto_error=False) extracts it and adds a security scheme to OpenAPI. With auto_error disabled your dependency explicitly chooses the missing-key policy rather than inheriting version-dependent defaults. Return a role such as reader/writer; require writer for POST/PATCH/DELETE. A valid read key can list/get. Reuse this dependency for all five task operations; public health and docs remain readable.

Read .env.example as documentation only. It contains public dummy localhost keys. No dotenv loader is configured: a file named .env does not automatically change Python's environment. Read settings once during app creation, using explicit environment values or documented local-only defaults; tests set both variables with monkeypatch. Real credentials are never required for this course and never belong in logs or an exported collection.

In dependencies.py, author key extraction, role checks and service lookup from request.app.state.service. Authentication answers “which trusted identity?”; authorization answers “may it perform this action?” An API key is not per-user ownership or production account management. This small read/write split gives a concrete 403 case without expanding into OAuth.

Make injection observable before using it for auth

Read get_prefix and create_dependency_app in practice/mechanisms.py. This completed example supplies a greeting prefix and does not implement project authentication. The endpoint declares prefix: Annotated[str, Depends(get_prefix)]. On a request, FastAPI calls get_prefix, receives Hello and passes that value into the endpoint. The endpoint combines it with learner and returns the message. The client did not supply prefix in a body or query.

It helps to mentally expand the arrangement into ordinary calls: first value = get_prefix(), then use value as the message function's prefix. In the actual app FastAPI arranges those calls from the declarations. You pass the callable to Depends without parentheses so the call happens when the dependency is resolved.

A controlled replacement

Read test_dependency_and_override in practice/test_mechanisms.py. It calls the same endpoint three times. First the normal dependency returns Hello. Then app.dependency_overrides[get_prefix] = lambda: "Welcome" replaces the supplier and the result changes to Welcome. A finally block clears the override, so the last response returns to Hello. A lambda here is just a small function returning a fixed string.

From the weekly root, run:

UV_CACHE_DIR=/tmp/week4-uv-cache uv run --locked --project projects/task-api pytest practice/test_mechanisms.py -k dependency -q

Expect one passing test with three response assertions. Record the supplier → injected argument → output trace in weekly-logs/week-04.md. Next explain why this replacement improves test control without proving that a real authentication dependency works.

Do not override authentication in tests whose purpose is to prove authentication. An always-allow substitute can make a broken protection layer look healthy. Use overrides to isolate something deliberately, and name what was replaced. The supplied Task contract sends real dummy headers through your dependency precisely because auth behavior is being assessed.

Apply the mechanism to permissions

For the project, key extraction produces a header value; identity checking produces an allowed role or raises; write permission decides whether that role can mutate. Authentication failure should stop protected work. A service lookup dependency, by contrast, supplies an object belonging to this app. They use the same injection mechanism for different purposes. In your log label each dependency “supplies a value,” “enforces a condition,” or both, and explain your choice.

First hint

A passing dependency replacement test proves replacement behavior, not every behavior of the replaced callable.

Reasoned answer

The greeting test proves which callable supplied the endpoint argument and that clearing the override restores it. It does not prove missing/wrong API keys are rejected. Those require requests that exercise the real key checker, including the negative cases on every endpoint.
