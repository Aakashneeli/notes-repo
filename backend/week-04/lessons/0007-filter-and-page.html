Filter first, then take a page

Two passes: first understand and predict; then run the guided check. Pause between sections when needed. Worked mechanism and debugging practice.

Return a useful total without losing False.

Pagination limits how much a list endpoint returns. This week uses offset (how many matching records to skip) and limit (how many to return). Defaults are 0 and 20; offset must be nonnegative, limit 1–100. A stable order, ascending ID here, makes pages predictable. Filtering selects a subset before paging; total is the size of that subset, not the page length.

Trace records 1:false, 2:true, 3:true. Query done=true, offset=1, limit=1. Filter produces [2,3]; order stays [2,3]; total is 2; skip 1 then take 1 gives [3]. If you slice before filtering, you might return [2] and miscount. An offset beyond the end returns an empty items list while retaining total=2. An empty collection returns 200 with items=[], not 404: the collection exists.

An absent done filter means include both values. A supplied done=false means include only incomplete tasks. if done: cannot distinguish False from absence. Compare explicitly with None when deciding whether a filter was supplied. Query parsing belongs at the route boundary; your service may receive an already typed boolean or None.

Trace the slice without memorizing syntax

For matching rows [2, 3, 4, 5], offset=1 means begin at list position 1, which contains ID 3. limit=2 means take two rows. The slice is matching[1:3]; its end position is excluded, so positions 1 and 2 yield IDs [3, 4]. The end must be offset+limit. Using matching[offset:limit] would use 2 as an end position and return only ID 3 in this example.

Keep three numbers separate in your response: total matching records is 4; the requested limit is 2; the returned page length is 2 here. On the final partial page those last two numbers can differ. On an empty page, total can still be positive. The client needs total to reason about further pages; it cannot recover that value just by counting the returned items.

Build matching rows, sort that new list by id, compute total before slicing.

Explained answer — compare with your attempt
matching = sorted((r for r in rows if r["done"] == done),
                  key=lambda r: r["id"])
return {"items": matching[offset:offset + limit], "total": len(matching)}

The generator selects; sorted builds a new list; the lambda returns the ID used for ordering. The slice end is offset+limit, not limit. This small answer is not the project route or service implementation.
