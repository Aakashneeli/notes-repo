Week 09 / Lesson 07

Read a trace without double-counting time

Use nested observations to locate a slow or failed operation.

A run records one operation. A trace connects related runs into a hierarchy: request → graph → nodes → tool/model calls. A backend log is an event such as “request finished”; correlated logs are useful, but a trace directly shows parent/child relationships, timings and recorded inputs/outputs. Both can leak data if carelessly collected.

Trace a synthetic request

Start at the weekly root. Read practice/trace_sample.json; it is supplied synthetic data, not downloaded LangSmith evidence. The root spans 0–130ms; retrieve spans 2–22ms and answer spans 22–122ms. Thus answer takes 100ms and dominates this sequential request. Summing root plus all children counts the same elapsed time twice. If children overlap, even summing children may overstate elapsed wall time.

A slow request may be waiting on a queue before a model begins. Inspect where time is spent rather than assuming the largest model is always the cause. A successful root with a caught tool exception can contain an errored child: graceful fallback does not erase the failed tool operation.

Instrumentation is ordinary wrapping

Read the @traceable functions in bridge.py. The search wrapper is marked retriever, lookup is tool, and deterministic generation is chain. It is not marked llm because no model was called. Nested calls within an active traced operation become children. LangGraph itself supplies node-level tracing; you do not need to decorate every line.

Trace metadata should include versions and case labels. It must not include credentials. Client-side state “private” fields are not a promise that telemetry hides them. For this course, keep tracing off until you deliberately run the fictional live suite.

Exercise with immediate feedback

Edit slowest in exercises.py. It receives flat, nonoverlapping sibling spans, each with name/start_ms/end_ms; the test has a unique maximum. Return the slowest name. From the weekly root:

.venv/bin/python -m pytest practice/test_exercises.py -k slowest -q
Hint — open after trying

Duration is end minus start. You are comparing durations, not absolute end times.

Explained answer — compare with your attempt

return max(spans, key=lambda span: span["end_ms"] - span["start_ms"])["name"]. max selects an item using the duration key; indexing then returns its name. A loop tracking the greatest duration is equally valid. This contract deliberately excludes empty input and ties.

Variation: create a late short span starting at 1000ms and ending at 1001ms. It should not beat an earlier 100ms span. Add that case and save the result in the weekly log. Write a one-paragraph diagnosis for the synthetic trace before looking at a live UI.

Trace ≠ evaluation

A trace can tell you that answer ran and returned text. It cannot by itself tell you the answer was useful or supported. Evaluation adds expected behavior and a judgment. Compare two runs of the same question, corpus and model while changing only prompt version; record both latency and answer support. A faster incorrect answer is not an improvement. Keep this distinction for the next lab.
