Week 09 / Lesson 11

Choose serving for the workload

Write a defensible vLLM concept note without requiring a GPU deployment.

A hosted API, a local runtime and a serving engine solve different operational problems. The model's quality still matters. Replacing a provider with a local server cannot fix poor retrieval or an inadequate model.

Latency and throughput are different questions

Latency is how long one request waits. Throughput is how much work finishes per unit time. Imagine two requests: A generates 3 tokens, B generates 6. A server that waits for both before admitting C can leave capacity unused after A finishes. Continuous batching can admit new work as existing requests finish. This is an illustrative schedule, not a throughput benchmark.

vLLM focuses on efficient model serving, including batching and management of attention key/value cache. GPUs matter because the model's numerical work benefits from parallel compute and memory bandwidth; available accelerator memory bounds the model and concurrent contexts. Supported non-GPU backends exist, so “vLLM can only run on NVIDIA” is too strong. This week's no-usable-GPU baseline makes it a concept study, not a deployment requirement.

An API adapter does not make behavior identical

An OpenAI-compatible API uses familiar HTTP paths and request/response shapes, such as messages in a chat-completions request. It does not guarantee identical model names, supported fields, chat templates, structured output or tool-call behavior. Pointing an adapter at a different base URL requires contract tests.

Illustrative production command shape, not a command to run on this machine: vllm serve MODEL_ID --host 127.0.0.1. A prepared deployment would first verify hardware/backend, package version, model support, revision, license, context/memory limits and access controls. No cloud machine or GPU is being provisioned in this week.

Worked decision and failure case

Suppose your CPU probe produces answers in 2 seconds for one user but becomes unusable at eight simultaneous requests. You cannot infer that a GPU server is economical from that alone: measure required quality, workload duration, token lengths and hosted cost too. If most hours have no traffic, owning a constantly running accelerator could be wasteful. If stable high concurrency and privacy needs justify operations, benchmark a suitable vLLM deployment before choosing it.

A common mistake is to optimize tokens per second while ignoring wrong answers. Another is to compare a short-output model against a long-output model without normalizing workload. Use the same prompts, bounds and quality checks.

Explained answer — compare with your attempt

For a low-volume learning app without a GPU, local inference is useful for privacy/offline experimentation but may fail quality or latency requirements. A hosted model can reduce operations. vLLM becomes a candidate with sustained load, suitable hardware and an operational reason to self-host—not merely because the endpoint shape looks familiar.
