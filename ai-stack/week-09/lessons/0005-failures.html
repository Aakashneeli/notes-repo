Week 09 / Lesson 05

End safely when evidence is weak

Implement validation and fallback while keeping failures diagnosable.

A graph makes intermediate decisions visible. It does not make bad evidence good. Your answer node should only run when you have useful authorized hits. Your validation node should reject malformed or unsupported citation IDs before returning a response.

Trace weak retrieval before coding

For weak, the fixture returns score 0.2. With our teaching threshold 0.5, retained hits are empty. Route to fallback, set reason=weak_retrieval, clear citations, write the fixed abstention and END. The generator should never run. The score is a fixture value, not a calibrated probability of truth; real thresholds depend on encoder, metric and data.

For bad citation refund, retrieval succeeds but generation returns ID “foreign”. The validator compares cited IDs with IDs in authorized hits. It rejects that ID, writes invalid_answer and falls back. A valid citation ID can still accompany a false sentence; checking membership is necessary but not sufficient for factual support.

A worked validation mechanism in a tiny example

allowed = {'T-01', 'T-02'}
proposed = ['T-01', 'T-99']
print(all(item in allowed for item in proposed))  # False
print(all(item in allowed for item in []))        # True

A set supports membership checks. The generator expression produces one Boolean per item; all requires all of them to be true. The empty case shows why you must separately require nonempty citations. Also validate the container and each element's type before using it; a dictionary or a string is not the intended list of IDs.

Explained answer — compare with your attempt

Weak retrieval must skip generation; malformed output must discard the draft; tool timeout is distinct from “no matching document”. An END edge and a bounded invocation prevent accidental endless work. A recursion limit does not interrupt a slow network socket: real clients need their own timeouts.

State is not persistence

Ordinary invocation carries state for that run. A checkpointer can retain snapshots for a thread; a store can retain application data across threads. A thread ID labels a checkpoint history, not an authenticated user. In-memory checkpoints disappear on restart. The assessed API deliberately uses fresh runs; accidental shared state could leak an earlier answer.

Read the optional memory=True branch in the completed example. From the weekly root, run this small persistence experiment:

graph.invoke({'text':'outage'}, config)
print(graph.get_state(config).values['queue'])
print(graph.get_state({'configurable': {'thread_id':'blue-2'}}).values)
PYCODE
