Week 09 / Lesson 10

Measure one real CPU model

Separate download/load costs, warm inference and answer quality.

The required lab is one small local model or embedding model through Transformers, Ollama or llama.cpp. The primary path here is Transformers with the model chosen in Lesson 9. You do not have to install all three engines. This is inference: using existing weights, not training them.

Check resources before running

Start at the weekly root. Run lscpu, free -h and df -h .; record relevant hardware, available RAM and disk in local-inference.md. Keep unrelated machine details private. Approximate raw weight memory: 135 million values × 4 bytes ≈ 540 MB in float32, before runtime, tokenizer, activations and attention cache. Download dtype may differ. Reserve several GB of free disk for packages/cache and measure peak process RAM rather than trusting this estimate.

A context uses memory too. Longer prompts and more simultaneous requests can exhaust memory even when weights fit. Stop with Ctrl-C if the machine begins swapping heavily; reduce scope or record a hardware blocker. No paid GPU is required or provisioned.

Install a separate inference environment

The core .venv stays small. These are learner-run network downloads into a separate .model-venv/ and an ignored cache. The CPU PyTorch wheel index avoids pulling a GPU runtime. Versions are bounded for this optional path; save the exact resolved versions with the result. The runner prints them in its report.

uv venv .model-venv --python 3.12
uv pip install --python .model-venv/bin/python 'torch>=2.6,<3' --index-url https://download.pytorch.org/whl/cpu
uv pip install --python .model-venv/bin/python 'transformers>=4.46,<5' 'huggingface-hub>=0.26,<1'
export HF_HOME="$PWD/runtime/hf-cache"
read -rp 'Full model revision SHA from Lesson 9: ' MODEL_REVISION
.model-venv/bin/python practice/local_model.py --revision "$MODEL_REVISION" --out runtime/inference/attempt-01.json

Expect a fresh JSON report path, not a promised answer string. The first run downloads weights; subsequent runs can use the local cache. A denied network, missing weight format, unsupported wheel or memory error is an environment blocker: retain the error and versions, do not fabricate results. Public ungated weights should not need a paid account. The probe does not upload prompts.

Understand the supplied runner

It pins the model revision, loads a matching tokenizer/model, uses two PyTorch CPU threads and runs three prompts twice. perf_counter measures elapsed wall time; process_time measures process CPU time. CPU time can exceed wall time when multiple threads work. Linux ru_maxrss is a process lifetime peak in KiB, not a per-prompt allocation and not the whole machine's RAM. The script separates initial load time from generation time. Inspect results; do not edit generated JSON to improve them.

The three tasks test simple grounded recall, structured output and abstention when context lacks an answer. First predict likely failure modes, then inspect each raw output. Mark “correct”, “unsupported”, “invalid JSON”, “truncated” or another justified category. A small model producing fluent text may still fail these tasks.

Record cold/load time, warm repeated timings, CPU behavior, peak RAM and qualitative limits in local-inference.md. Keep raw output in runtime and preserve a concise excerpt/table in the tracked note. Variation: from the weekly root run cp -n practice/local_model.py practice/local_model_variation.py to make your own copy (preserve it if it already exists), change only max_new_tokens to 64, save to a fresh report, and explain the latency/completeness tradeoff. Do not change model and token budget simultaneously.

Optional comparison after your attempt: maintenance/author-inference.json is supplied tutor verification output, not your progress. Read it to compare failure categories; leave it unchanged. The author run answered the simple fact, but failed strict JSON and invented an unsupported policy. Its model-default temperature warning was ignored under nonsampling decoding; a completed call did not imply valid output. Repeat on your own machine before claiming the lab.

Alternative path: an already installed Ollama

Ollama manages model artifacts and a local service. If you already have it, you can use a small available model instead; inspect its license/model identity and ensure adequate space first. From the weekly root, with the service running locally:

ollama pull smollm2:135m
curl http://127.0.0.1:11434/api/generate -H 'Content-Type: application/json' -d '{"model":"smollm2:135m","prompt":"Reply with the number of days: Refunds take 30 days.","stream":false,"options":{"num_predict":32,"temperature":0}}'

Pull downloads weights. A connection-refused error means the local service is unavailable; use official setup instructions for your platform if you choose this path. The response contains text and timings; Ollama duration metrics are nanoseconds. Compute generation rate as eval_count ÷ (eval_duration / 1e9), guarding zero duration. Repeat the three primary probe tasks and collect hardware/quality evidence; this must be a real run, not the example response from documentation. Do not expose the service port publicly.

llama.cpp and GGUF awareness

llama.cpp is an inference engine with CPU and other backends. GGUF is a model file format that carries tensors and metadata. Quantization uses reduced numeric precision to reduce weight storage, often trading some quality; GGUF does not itself mean a particular quantization level. A quantized model still needs runtime/context memory. If choosing this route, use a compatible official build and a documented GGUF conversion/quantized artifact; record its source, license and quantization. A generic command shape is llama-cli -m path/to/model.gguf -p 'Your prompt' -n 32, with the actual installed build and artifact checked first. This alternative is not executed by course preparation.

Recall: why isn't download time warm inference latency? Why can a “small file” still use more RAM? Next, use measurements to choose a serving approach.
