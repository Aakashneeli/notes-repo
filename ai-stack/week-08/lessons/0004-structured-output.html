Week 08 / Lesson 04

Validate an answer, then decide whether to retry

Separate JSON syntax, schema validity and evidence support.

JSON is a notation; a schema specifies its allowed shape; application checks decide whether values are acceptable. None of these by itself establishes truth. {"answer":"90 days","citations":["c1"]} is syntactically valid even when c1 says 30 days.

Three gates

Read Answer and parse_answer in examples.py. BaseModel defines named fields. answer: str and citations: list[str] are type declarations used by validation. Strict mode avoids unwanted coercion; extra fields are forbidden. model_validate_json combines parsing and schema validation. The separate allowed-ID test checks context membership.

A plain string containing fenced Markdown would fail JSON parsing unless deliberately preprocessed; do not silently strip arbitrary text to make failures disappear.

Pydantic's model documentation is the source for the local validation mechanism. The provider's structured-output documentation describes JSON-schema request configuration. Model support varies; JSON object mode and strict schema mode are distinct. Even a schema-conforming reply still needs application checks.

A bounded repair trace

To connect the local schema to a compatible provider request, generate the schema with Answer.model_json_schema(). It describes an object with required answer/citations fields, string/list item types and no additional properties. The request fragment below belongs beside model/messages in a provider body; first verify that your selected model supports it. This changes generation constraints, not the local checks:

response_format = {
    "type": "json_schema",
    "json_schema": {
        "name": "cited_answer",
        "strict": True,
        "schema": Answer.model_json_schema(),
    },
}

From the weekly root, inspect without sending a request: .venv/bin/python -c "from practice.examples import Answer; print(Answer.model_json_schema())". Expect required answer/citations and additionalProperties=False. If the provider rejects the schema or model feature, diagnose that configuration error; it is not an invalid-output repair attempt. Record the distinction in your weekly log before continuing.

For this lab, permit at most two generation calls. Attempt 1 returns citations as a string. Catch the validation error, ask for the required shape using a short sanitized repair instruction, and try once more. Attempt 2 returns a valid structure: continue. If it also fails, raise the generic invalid-output error. Do not recursively retry forever. Timeouts and credential failures are different failure classes; this parsing function must not retry them.

Guided diagnosis

A reply contains {"answer":30,"citations":["c1"]}. What fails? What if the answer is the string “30” but c1 belongs to another tenant?

Hint

Check type first, then trace where allowed IDs came from.

Explained answer

The number fails strict string validation. The second can pass schema validation; safe retrieval must exclude the other tenant before prompt construction, and citation checking must allow only supplied IDs. If that private chunk already entered the prompt, output validation cannot undo the disclosure.
