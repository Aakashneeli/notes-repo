Week 08 / Lesson 12

Choose a store with a reason

Compare setup, filters, persistence and deployment fit without extra provisioning.

The roadmap permits a conceptual comparison when setup time is tight. You already practised one real local store; now compare Qdrant with pgvector and understand where Chroma and a managed service differ. An evidence-backed choice is more useful than installing four products.

Questions to investigate, with starting distinctions
OptionSetup and data modelDecision pressure
Qdrant localPython client, embedded persistent path, points/payload/filterSimple small lab; server deployment/concurrency must be assessed separately
pgvectorPostgreSQL extension; vector columns beside relational data; SQL WHERE clausesFits an existing Postgres operational boundary; extension/index/query choices add work
ChromaCollection-oriented document/embedding API with persistent-client optionsCheck embedding defaults, filtering and local versus server topology explicitly
Pinecone-style managedHosted index, record IDs/vectors/metadata, account and network boundaryOffloads some operations; adds service cost, data-location and provider dependency decisions

Use the pgvector project documentation, Chroma getting-started guide and Pinecone data-model guide to verify these starting distinctions. This table is not a claim that one store universally wins or that managed filtering is authorization by itself.

Understand the SQL analogy

-- Conceptual only: extension-enabled PostgreSQL, not run in this lab
SELECT chunk_id, text
FROM chunks
WHERE tenant = 'red'
ORDER BY embedding <=> '[1,0,0]'
LIMIT 3;

The filter scopes records; the distance expression orders them; LIMIT bounds the result. For cosine distance, smaller is closer, whereas the Qdrant cosine score is ranked larger-first. Do not copy a threshold unchanged between distance and similarity. The SQL needs a real schema, extension and dimension declaration before execution; do not run it against an earlier learner database without a separate migration plan.

Guided scenario: your production backend already operates PostgreSQL and needs relational ownership checks. What favors pgvector, and what remains uncertain?

Hint

Consider the number of operational systems, then separate that from measured retrieval latency.

Explained answer

Keeping source metadata and vectors near existing relational ownership can reduce integration boundaries. That does not prove query latency, index behavior or operational capacity for your workload. State those as measurements needed rather than inventing benchmarks.

Independent variation: a second application needs a separately scalable retrieval service. Revisit the choice and list one benefit and one new failure boundary. No hosted account or paid service is needed for this note.
