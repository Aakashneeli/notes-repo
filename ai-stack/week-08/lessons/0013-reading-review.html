Explain the pipeline without copying

Collect independent evidence, review code boundaries and schedule retrieval.

Now assess ownership: can you rebuild a small piece, explain a failure and vary it with fewer hints? Reading all pages or passing author checks does not answer that.

In a second short note, trace your own create_app → search → answer boundary. Identify where a dictionary becomes JSON and where an injected provider is called. Explain why a mock proves call/validation behavior but not factual grounding. Cross-link one test to one claim.

Git as evidence

# Start: weekly root
git status --short
git diff -- projects/manual-rag/rag.py
git diff --check

Untracked files do not appear in an ordinary diff, so inspect status and open new files too. Do not stage existing unrelated learner work. After reviewing your own implementation, use explicit paths:

git add projects/manual-rag/rag.py projects/manual-rag/decisions.md
git diff --cached --stat
git diff --cached --check

Check that only intended content is staged before making your own commit. Do not commit secrets, runtime databases or model weights. Creating these materials did not commit anything. Record a commit ID only after you create one; a staged change is not a historical checkpoint.

Verification is not learning

Read VALIDATION.md for author checks and limits. maintenance/verify.py checks navigation, map coverage and syntax; maintenance/test_examples.py checks completed fragments and deliberately broken variants. Leave these tutor-maintained files unchanged unless improving the course. Run from the weekly root:

.venv/bin/python maintenance/verify.py
.venv/bin/python -m pytest maintenance -q

These should pass even while your project is unfinished. Run the separate project/practice suites for your implementation. A course-author pass cannot tick a learner completion box. Read the teaching review for the distinction between coverage, working code and a teachable progression.

Delayed retrieval

After roughly two days, reconstruct one query trace without the diagram. After roughly a week, implement a small changed requirement—such as a different chunk size or an unknown-question policy—and predict affected tests before running them. Dates are flexible; the gap matters more than a streak.
